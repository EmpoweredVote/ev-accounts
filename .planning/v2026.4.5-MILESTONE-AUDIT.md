## Integration Findings

### BLOCKER: STATE-01 CTA Unreachable in Elections for Null polIdKey Candidates

**Affected requirements:** STATE-01, ADOPT-02

In `ElectionsView.jsx` line 622, `polIdKey` is derived from the candidate's linked politician ID. When this is null/undefined (candidate has no linked politician record), `politicianIdsWithStances.has(polIdKey)` returns `false`. This forces `computeVariant` to return `'no-stances'` regardless of the user's calibration level — the user never sees the "Build your compass" CTA for these candidates. Core wiring is correct for candidates WITH a polIdKey.

**Fix:** Guard `polIdKey` explicitly: if `!polIdKey`, fall through to check `rawUserAnswers.length < 3` for the empty/CTA variant rather than defaulting to `no-stances`.

### WARNING: PlaceholderRadar Not Barrel-Exported (Phase 127 SUMMARY Incorrect)

**Affected requirements:** CARD-01

`ev-ui/src/index.js` exports `CompassCardHorizontal`, `CompassCardVertical`, and `IconOverlay` but NOT `PlaceholderRadar` or `compassHelpers.js`. Phase 127 SUMMARY claims they are barrel-exported — this is wrong. `PlaceholderRadar` is imported internally by `CompassCardVertical` and renders correctly; this does not break production. But any future consumer that tries `import { PlaceholderRadar } from '@empoweredvote/ev-ui'` would get a runtime error.

## Key Architectural Finding

Phase 127/128 built `CompassCardHorizontal` (prototype/harness vehicle) and Phase 129 adopted `CompassCardVertical` (production card). The horizontal card is published in ev-ui but not used in production — `CompassCardVertical` with the `variant` prop from `computeVariant` is the production surface. The CARD requirements are satisfied at the library level (component published, exported, functional) but their production-usage story lives in CompassCardVertical. ADOPT requirements correctly reflect this.
