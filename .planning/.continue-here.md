## Immediate blocker: Render deploy failing

The deploy of fc1aa40 fails because `campaignFinanceInit()` at backend startup does:
```typescript
await pool.query('SELECT 1 FROM transparent_motivations.politician_sources LIMIT 1');
```
If pg-pool times out (connectionTimeoutMillis: 5000, max: 5), this throws, the IIFE in
index.ts propagates the unhandled rejection, and Render marks the deploy as failed.

Root cause confirmed: `backend/src/index.ts` line 137 — `await campaignFinanceInit()`
with no try/catch around it. On pg-pool connection timeout at startup → process exits.

**Fix options (in priority order):**
1. **Retry the deploy** from Render dashboard — if pg-pool is intermittently flaky,
   a retry might succeed during a good window.
2. **Make campaignFinanceInit non-fatal** in `backend/src/index.ts`:
   ```typescript
   try { await campaignFinanceInit(); } catch (e) { console.warn('[startup] campaign-finance schema unreachable:', e); }
   ```
3. **Increase connectionTimeoutMillis** in `backend/src/lib/db.ts` from 5000 → 15000
   to give more headroom during startup.

## Supabase pg-pool connection timeouts (pre-existing)

All routes using pool.query (referral, jurisdiction, invites/my-invitees) return 500.
Routes using supabase JS client work fine.

pool config: `DATABASE_URL` (direct port 5432), `max: 5`, `connectionTimeoutMillis: 5000`

**Check in Render env vars:** Verify DATABASE_URL still points to correct Supabase project.
Supabase sometimes rotates passwords or changes connection strings.

**Consider switching** DATABASE_URL to the Supabase pooler connection string (port 6543)
instead of direct postgres (port 5432) — the pooler handles more concurrent connections.
