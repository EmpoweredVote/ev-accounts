### Section 2: Platform Context

Title: "Empowered Vote Platform Overview"

Explain from scratch (zero prior context assumed):
- Empowered Vote is a civic engagement platform with three tiers: Inform, Connected, Empowered.
- **Inform** = unauthenticated or pre-signup. Can browse all public content. Compass answers are local-only (server returns null on POST, empty arrays on GET).
- **Connected** = signed up via invite code, verified email. Full read/write access. Has a connected_profile with XP, gems, verification rating. Can access jurisdiction if location consent granted.
- **Empowered** = promoted from Connected. Has legal name on file, candidate page. For compass purposes, identical to Connected.
- Tier is determined by child record presence: `connected_profiles` row exists = Connected, `empowered_profiles` row exists = Empowered. The `tier` field in /account/me response reflects this.
- Auth is via Supabase (PostgreSQL + JWT). Tokens are Supabase JWTs with ~1 hour expiry.

### Section 3: Authentication Flow

Title: "Authenticate a User"

Explain the full redirect flow with rationale:

**Why redirect:** CompassV2 does not handle login/signup directly. Users authenticate at accounts.empowered.vote (the Auth Hub) and return with a token. This centralizes auth for all Empowered Vote apps.

**Step 1 — Redirect to Auth Hub:**
When user needs to authenticate, redirect to:
```
https://accounts.empowered.vote/login?redirect={encodeURIComponent(window.location.href)}
```
Only `*.empowered.vote` domains are accepted as redirect targets. Any other domain is silently discarded.

**Step 2 — User authenticates at Auth Hub:**
The Auth Hub handles login, signup (with invite code), and email verification. On success, it redirects back to the `redirect` URL with the token as a hash fragment:
```
https://compassv2.empowered.vote/some-page#access_token=eyJhbGciOiJI...
```

**Why hash fragment, not query param:** Query parameters are logged by servers, proxies, CDNs, and browser history. Hash fragments never leave the browser — they are client-side only. This prevents token leakage.

**Step 3 — Extract token on return:**
Provide BOTH HTTP concept and TypeScript implementation:

```typescript
// On app initialization or route change
function handleAuthReturn(): string | null {
  const hash = window.location.hash;
  if (!hash.includes('access_token=')) return null;

  const params = new URLSearchParams(hash.substring(1));
  const token = params.get('access_token');
  if (!token) return null;

  // Clean URL immediately — token should not persist in address bar
  window.history.replaceState(null, '', window.location.pathname + window.location.search);

  // Store token
  localStorage.setItem('ev_token', token);
  return token;
}
```

**Step 4 — Use token for API calls:**
```typescript
const response = await fetch(`${API_BASE}/account/me`, {
  headers: { Authorization: `Bearer ${token}` }
});
```

**Token lifecycle:**
- Supabase JWTs expire in ~1 hour.
- When any API call returns 401 AUTH_ERROR, clear the stored token and redirect to Auth Hub.
- There is no refresh token flow exposed — re-authenticate via redirect.

Include anti-pattern blockquote:
> **Anti-pattern:** Do not call POST /auth/login directly from CompassV2. The redirect flow is the only supported auth mechanism for external apps. Direct login is for the accounts app itself.

Title: "Read and Write User Answers"

**GET /api/compass/answers**
- Auth: Optional
- Unauth: Returns `[]`

```typescript
interface UserAnswer {
  topic_id: number;
  value: number;          // 0.5 to 5.5, step 0.5
```

**POST /api/compass/answers**
- Auth: Optional
- Request body: `{ topic_id: number, value: number, write_in_text?: string }`
- Value constraint: `0.5 <= value <= 5.5`, must be a multiple of 0.5. Parse as float, not integer.
- Unauth response: `null` (answer accepted locally but NOT persisted server-side)
- Auth response: The saved answer object

Include anti-pattern blockquote:
> **Anti-pattern:** Do not treat a `null` response from POST /compass/answers as an error. For Inform (unauthenticated) users, `null` IS the success response — it means the server acknowledged the request but cannot persist without an account.

> **Anti-pattern:** Do not parse answer values as integers. The `value` field is NUMERIC and may be a float like 3.5. Always use parseFloat, never parseInt.

**POST /api/compass/answers/batch**
- Auth: Optional
- Request body: `{ ids: number[] }` (array of topic IDs)
- Unauth: Returns `[]`
- Auth: Returns array of `{ topic_id, value, write_in_text? }` for the requested topic IDs

**GET /api/compass/selected-topics**
- Auth: Optional

**PUT /api/compass/selected-topics**

- Unauth: Returns `{ topic_ids: [] }` (not persisted)
- Auth but NOT Connected: Returns 403 with code `NOT_CONNECTED`
- Auth + Connected: Returns `{ topic_ids: number[] }`

Include anti-pattern blockquote:
> **Anti-pattern:** Do not expect GET /compass/selected-topics to return 403 for anonymous users. It returns an empty array. The 403 NOT_CONNECTED only fires on PUT when an authenticated-but-not-Connected user tries to save.

### Section 7: Jurisdiction — The "Never Ask for Address" Principle

Title: "Jurisdiction and Location Personalization"

This must be a FIRST-CLASS section, not a footnote. Explain:

**The principle:** If a user has granted location consent and their jurisdiction is resolved, CompassV2 MUST use it to personalize content (filter politicians by district, show relevant local topics) WITHOUT ever prompting the user for their address. The address was collected once during account setup. Asking again is a product violation — it signals the platform doesn't trust its own data.

**How it works:**
1. User grants location consent during account setup (at accounts.empowered.vote)
2. Accounts resolves their address to legislative districts via Census geocoder
3. The jurisdiction object appears in GET /api/account/me when `location_consent === true` AND user is Connected+

**Jurisdiction object shape:**
```typescript
interface Jurisdiction {
  congressional_district: string | null;
  congressional_district_name: string | null;
  state_senate_district: string | null;
  state_senate_district_name: string | null;
  state_house_district: string | null;
  state_house_district_name: string | null;
  county: string | null;
  county_name: string | null;
  school_district: string | null;
  school_district_name: string | null;
}
```

**Usage in CompassV2:**
```typescript
// Personalize politician list by district
if (me.jurisdiction) {
  const myDistrict = me.jurisdiction.congressional_district;
  // Filter or highlight politicians in user's district
}
```

**When jurisdiction is null:**
- User is Inform (not authenticated) — show all content, no personalization
- User is Connected but has not granted location consent — show all content, do NOT prompt for address
- User granted consent but geocoding hasn't resolved yet — show all content, jurisdiction will appear on next /me call

Include anti-pattern blockquote:
> **Anti-pattern:** Do not prompt the user for their address, zip code, or location if `jurisdiction` is null. The null means either they haven't consented (their choice) or resolution is pending. In both cases, show the full unfiltered experience. Location collection is exclusively handled by the accounts app.

### Section 9: Error Handling

Title: "Error Handling"

All API errors return:
```json
{ "code": "ERROR_CODE", "message": "Human-readable description" }
```

Always parse `code`, never `message` (message text may change).

**Error codes relevant to CompassV2:**

| Code | HTTP | Meaning |
|------|------|---------|
| AUTH_ERROR | 401 | Token missing, expired, or invalid. Clear token, redirect to Auth Hub. |
| NOT_CONNECTED | 403 | User is authenticated but not Connected tier. Show upgrade prompt. |
| VALIDATION_ERROR | 422 | Request body failed validation. Check field constraints. |
| INVALID_TOPIC_IDS | 422 | One or more topic IDs in request don't exist. |
| TOPIC_NOT_FOUND | 404 | Single topic ID not found. |
| NOT_FOUND | 404 | Resource not found. |
| INVALID_CREDENTIALS | 401 | Login failed (only relevant for direct auth, not CompassV2). |
| EMAIL_NOT_VERIFIED | 403 | Email not yet verified. |
| EMAIL_EXISTS | 409 | Signup with existing email. |
| INVALID_INVITE_CODE | 422 | Bad invite code on signup. |
| SELF_INVITE_BLOCKED | 422 | User tried to use their own invite code. |
| RATE_LIMIT_EXCEEDED | 429 | Too many requests. Back off and retry. |
| EMAIL_DELIVERY_FAILED | 503 | Email service error. |
| USER_NOT_FOUND | 404 | User lookup failed. |
| INTERNAL_ERROR | 500 | Server error. Retry with backoff. |

Include anti-pattern blockquote:
> **Anti-pattern:** Do not store tier status client-side across sessions. Always re-read /api/account/me at session start. Tier can change (e.g., user gets promoted to Empowered, or account gets suspended) between sessions.

> **Anti-pattern:** Do not store tokens without handling AUTH_ERROR. When any API call returns 401 with code AUTH_ERROR, immediately clear the stored token and redirect to the Auth Hub. Stale tokens should never accumulate.

> **Anti-pattern:** Do not attempt to read `tolerance_rating` for other users. This is an owner-only field and is never returned for non-owning users.
