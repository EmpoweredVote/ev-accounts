Create integration test file following the existing test patterns in the project (check gems.test.ts for the service-key auth test setup pattern).

**Test setup:**
- Use the project's test infrastructure (supertest or equivalent — match existing test files)
- Configure a test service key that permits 'red' gem type (match how gems.test.ts sets up GEMS_SERVICE_KEYS)
- Create test users with connected_profiles (need at least 2-3 test users)
- Create a test politician and compass topic in the inform schema for the stance write tests
- Store initial verification_rating values for comparison

**Test cases (one describe block for POST /api/vq/confirm-stance):**

1. **Auth rejection** (VQ-01)
   - No Authorization header -> 401
   - Invalid Bearer token -> 401
   - Valid key without 'red' permission -> 422 FORBIDDEN_GEM_TYPE

2. **Validation errors** (VQ-01)
   - Missing required fields -> 422
   - Invalid UUID format for politician_id -> 422
   - confirmed_value outside 1-5 range -> 422
   - Empty idempotency_key -> 422

3. **Invalid question (politician/topic pair)** (VQ-01)
   - Non-existent politician_id -> 404 QUESTION_NOT_FOUND
   - Non-existent topic_id -> 404 QUESTION_NOT_FOUND

4. **Correct user processing** (VQ-02, VQ-03)
   - Send request with 1 correct user, verify:
     - Response has correct_count: 1
     - User result shows result: 'correct', gems_awarded > 0, rating_delta: 3
     - Query connected_profiles: verification_rating increased by 3
     - Query gem_transactions: red gem transaction exists with correct amount
     - Query gem_balance_red: increased by gems_amount

5. **Rating cap at 150** (VQ-03)
   - Set a test user's verification_rating to 149 (or 148)
   - Send correct answer -> new_rating should be LEAST(149+3, 150) = 150
   - Verify rating_delta reflects the capped amount

6. **Incorrect user processing** (VQ-04)
   - Send request with 1 incorrect user, verify:
     - Response has incorrect_count: 1
     - User result shows result: 'incorrect', gems_awarded: 0, rating_delta: -10 (or less if near floor)
     - Query connected_profiles: verification_rating decreased by 10
     - No red gem transaction for this user

7. **Rating floor and vq_hold_until** (VQ-04)
   - Set a test user's verification_rating to 5 (below 10)
   - Send incorrect answer -> new_rating should be 0
   - Query connected_profiles: vq_hold_until is set ~30 days from now
   - Response shows rating_delta reflecting drop to 0

8. **vq_hold_until overwrite on repeated floor hit** (VQ-04)
   - User already at rating 0 with existing vq_hold_until
   - Send another incorrect answer (new idempotency_key)
   - Verify vq_hold_until is reset/overwritten (new timestamp)
   - Rating stays at 0, rating_delta: 0

9. **Stance write** (VQ-05)
   - After a successful confirm-stance call, query inform.politician_answers
   - Verify row exists with correct politician_id, topic_id, value matching confirmed_value
   - Send another confirm-stance with different confirmed_value (new idempotency_key, same politician/topic)
   - Verify politician_answers row is updated (upsert, not duplicate)

10. **Idempotency replay** (VQ-06)
    - Send a confirm-stance call, record the response
    - Send the exact same request with the same idempotency_key
    - Verify response matches original + has replayed: true
    - Verify no additional gem transactions were created
    - Verify verification_rating unchanged from first call's result

11. **Unknown user handling**
    - Include a random UUID in correct_user_ids that doesn't exist in connected_profiles
    - Verify response includes the UUID in unresolved_users
    - Verify other valid users in the same request are still processed correctly

12. **Mixed correct and incorrect users**
    - Send request with both correct_user_ids and incorrect_user_ids populated
    - Verify each user is processed according to their list
    - Verify correct_count and incorrect_count are accurate

**Important test patterns:**
- Clean up test data after each test (or use unique idempotency keys to avoid conflicts)
- Use unique idempotency_key per test case to prevent cross-test interference
- Match the existing test file structure (describe/it blocks, assertion library)
- Check the actual DB state after calls, not just the HTTP response — the response could lie, the DB state is truth
