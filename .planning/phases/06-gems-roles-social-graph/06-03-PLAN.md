**`backend/src/lib/socialService.ts`** — Create social service following the empowerService.ts pattern:

```typescript
import { supabaseAdmin } from './supabase.js';
import { pool } from './db.js';
```

Functions to implement:

1. `sendPeerRequest(actorId: string, targetId: string): Promise<{ id: string; status: string }>`
   - Call `supabaseAdmin.schema('connect').rpc('create_peer_request', { p_actor_id: actorId, p_target_id: targetId })`
   - The RPC enforces: self-request rejection, bidirectional block check, duplicate prevention, declined re-send (deletes old row and inserts new pending)
   - On error, parse the RPC exception message to throw structured errors:
     - Message includes 'SELF_REQUEST' => throw with code `SELF_REQUEST`
     - Message includes 'BLOCKED' => throw with code `BLOCKED`
     - Message includes 'ALREADY_CONNECTED' => throw with code `ALREADY_CONNECTED`
     - Message includes 'PENDING' => throw with code `PENDING`
     - Otherwise throw generic error
   - Return `{ id: data.id, status: data.status }`

2. `acceptPeerRequest(requestId: string, userId: string): Promise<void>`
   - Use pool.query (single UPDATE, no multi-table atomicity needed):
   ```sql
   UPDATE connect.social_relationships
   SET status = 'accepted', updated_at = now()
   WHERE id = $1
     AND target_id = $2
     AND connection_type = 'peer'
     AND status = 'pending'
   ```
   - The WHERE ensures only the target (addressee) can accept, and only pending requests.
   - If `rowCount === 0`, throw with code `REQUEST_NOT_FOUND` (either doesn't exist, user isn't the target, or not pending)

3. `declinePeerRequest(requestId: string, userId: string): Promise<void>`
   - Same pattern as accept but sets `status = 'declined'`
   - WHERE clause: `id = $1 AND target_id = $2 AND connection_type = 'peer' AND status = 'pending'`
   - If `rowCount === 0`, throw with code `REQUEST_NOT_FOUND`

4. `blockUser(actorId: string, targetId: string): Promise<void>`
   - Use pool with a client (BEGIN/COMMIT transaction):
   - Step 1: Check if any peer relationship exists between the two users (either direction):
     ```sql
     SELECT id, status FROM connect.social_relationships
     WHERE connection_type = 'peer'
       AND ((actor_id = $1 AND target_id = $2) OR (actor_id = $2 AND target_id = $1))
     LIMIT 1
     ```
   - Step 2: If exists, UPDATE to `status = 'blocked'`, `actor_id = $1` (the blocker becomes the actor), `updated_at = now()`. This ensures the blocker is always recorded as actor_id on block rows.
     ```sql
     UPDATE connect.social_relationships
     SET status = 'blocked', actor_id = $1, target_id = $2, updated_at = now()
     WHERE id = $3 AND connection_type = 'peer'
     ```
   - Step 3: If no existing relationship, INSERT a new blocked row:
     ```sql
     INSERT INTO connect.social_relationships (actor_id, target_id, connection_type, status)
     VALUES ($1, $2, 'peer', 'blocked')
     ON CONFLICT (actor_id, target_id, connection_type) DO UPDATE SET status = 'blocked', updated_at = now()
     ```
   - Also remove any follow relationship between the two (in either direction):
     ```sql
     DELETE FROM connect.social_relationships
     WHERE connection_type = 'follow'
       AND ((actor_id = $1 AND target_id = $2) OR (actor_id = $2 AND target_id = $1))
     ```
   - Release client in `finally` block

5. `follow(actorId: string, targetId: string): Promise<void>`
   - Validate the target is an Empowered account (Connected users cannot be followed -- must use peer connection):
     ```sql
     SELECT id FROM empower.empowered_profiles WHERE user_id = $1 AND is_active = true
     ```
     If no row, throw with code `NOT_EMPOWERED` and message `Can only follow Empowered accounts`
   - Check the actor is not blocked by the target:
     ```sql
     SELECT 1 FROM connect.social_relationships
     WHERE connection_type = 'peer' AND status = 'blocked'
       AND ((actor_id = $1 AND target_id = $2) OR (actor_id = $2 AND target_id = $1))
     ```
     If found, throw with code `BLOCKED`
   - INSERT follow row using pool:
     ```sql
     INSERT INTO connect.social_relationships (actor_id, target_id, connection_type)
     VALUES ($1, $2, 'follow')
     ON CONFLICT (actor_id, target_id, connection_type) DO NOTHING
     ```
   - ON CONFLICT DO NOTHING makes follow idempotent (following twice is not an error)

6. `unfollow(actorId: string, targetId: string): Promise<void>`
   - DELETE using pool:
     ```sql
     DELETE FROM connect.social_relationships
     WHERE actor_id = $1 AND target_id = $2 AND connection_type = 'follow'
     ```
   - No error if no matching row (idempotent unfollow)

7. `getConnections(userId: string): Promise<Array<{ id: string; peer_id: string; display_name: string; status: string; created_at: string }>>`
   - Use pool.query:
     ```sql
     SELECT
       sr.id,
       CASE WHEN sr.actor_id = $1 THEN sr.target_id ELSE sr.actor_id END AS peer_id,
       up.display_name,
       sr.status,
       sr.created_at
     FROM connect.social_relationships sr
     JOIN public.users_public up
       ON up.id = CASE WHEN sr.actor_id = $1 THEN sr.target_id ELSE sr.actor_id END
     WHERE sr.connection_type = 'peer'
       AND (sr.actor_id = $1 OR sr.target_id = $1)
       AND sr.status IN ('pending', 'accepted')
     ORDER BY sr.updated_at DESC
     ```
   - Note: This excludes blocked and declined from the list. Include a `direction` field to indicate 'inbound' vs 'outbound' for pending requests:
     Add `CASE WHEN sr.actor_id = $1 THEN 'outbound' ELSE 'inbound' END AS direction` to the SELECT.

8. `getFollowing(userId: string): Promise<Array<{ id: string; target_id: string; display_name: string; created_at: string }>>`
   - Use pool.query:
     ```sql
     SELECT sr.id, sr.target_id, up.display_name, sr.created_at
     FROM connect.social_relationships sr
     JOIN public.users_public up ON up.id = sr.target_id
     WHERE sr.actor_id = $1 AND sr.connection_type = 'follow'
     ORDER BY sr.created_at DESC
     ```

9. `getFollowerCount(userId: string): Promise<number>`
   - Use pool.query:
     ```sql
     SELECT COUNT(*)::int AS count
     FROM connect.social_relationships
     WHERE target_id = $1 AND connection_type = 'follow'
     ```
   - Return the count integer. This is public for Empowered users (CONTEXT.md: "Follower count on Empowered profiles: public"). The route handler will check tier.

```typescript
// Role conflict groups: roles in the same group cannot be held simultaneously.
// Empty for Alpha — populated as roles are defined with conflict rules.
// Example future entry: { 'arbiter': 'judicial', 'juror': 'judicial' }
const ROLE_CONFLICT_GROUPS: Record<string, string> = {};
```

In the `grantRole` function, after the tier eligibility check and before the INSERT, add conflict enforcement:

```typescript
// CIVIC-04: Check for conflicting active roles
const conflictGroup = ROLE_CONFLICT_GROUPS[roleSlug];
if (conflictGroup) {
  // Find all role slugs in the same conflict group
  const conflictingSlugs = Object.entries(ROLE_CONFLICT_GROUPS)
    .filter(([, group]) => group === conflictGroup)
    .map(([slug]) => slug)
    .filter(slug => slug !== roleSlug);

  if (conflictingSlugs.length > 0) {
    const { rows: conflictRows } = await client.query(
      `SELECT r.slug FROM public.user_roles ur
       JOIN public.roles r ON r.id = ur.role_id
       WHERE ur.user_id = $1 AND ur.revoked_at IS NULL AND r.slug = ANY($2)`,
      [userId, conflictingSlugs]
    );
    if (conflictRows.length > 0) {
      throw Object.assign(
        new Error(`Role '${roleSlug}' conflicts with active role '${conflictRows[0].slug}'`),
        { code: 'ROLE_CONFLICT' }
      );
    }
  }
}
```

**Peer connection routes** (all require requireAuth + requireConnected):

Route 1: `POST /api/social/peers/request`
- Body: `{ target_id: string }` (validated with Zod `z.object({ target_id: z.string().uuid() })`)
- Call `sendPeerRequest(authReq.userId, body.target_id)`
- Return 201 with `{ request: { id, status } }`
- Error handling: map service error codes to HTTP status codes:
  - SELF_REQUEST => 422
  - BLOCKED => 403
  - ALREADY_CONNECTED => 409
  - PENDING => 409
  - Default => 500

Route 2: `PATCH /api/social/peers/:id/accept`
- No body needed
- Call `acceptPeerRequest(req.params.id, authReq.userId)`
- Return 200 with `{ accepted: true }`
- REQUEST_NOT_FOUND => 404, Default => 500

Route 3: `PATCH /api/social/peers/:id/decline`
- No body needed
- Call `declinePeerRequest(req.params.id, authReq.userId)`
- Return 200 with `{ declined: true }`
- REQUEST_NOT_FOUND => 404, Default => 500

Route 4: `POST /api/social/peers/block`
- Body: `{ target_id: string }` (Zod UUID validation)
- Call `blockUser(authReq.userId, body.target_id)`
- Return 200 with `{ blocked: true }`
- 500 on error

Route 5: `GET /api/social/peers`
- Call `getConnections(authReq.userId)`
- Return 200 with `{ connections: [...] }`

**Follow routes** (all require requireAuth + requireConnected):

Route 6: `POST /api/social/follow`
- Body: `{ target_id: string }` (Zod UUID validation)
- Call `follow(authReq.userId, body.target_id)`
- Return 201 with `{ following: true }`
- Error handling:
  - NOT_EMPOWERED => 422 with message "Can only follow Empowered accounts"
  - BLOCKED => 403
  - Default => 500

Route 7: `DELETE /api/social/follow/:target_id`
- Call `unfollow(authReq.userId, req.params.target_id)`
- Return 200 with `{ unfollowed: true }`

Route 8: `GET /api/social/following`
- Call `getFollowing(authReq.userId)`
- Return 200 with `{ following: [...] }`

Route 9: `GET /api/social/followers/count/:user_id`
- Middleware: requireAuth only (no requireConnected -- any authenticated user can see an Empowered user's follower count)
- Validate that the target user is Empowered (query `empower.empowered_profiles WHERE user_id = :user_id AND is_active = true` via pool). If not Empowered, return 404.
- Call `getFollowerCount(req.params.user_id)`
- Return 200 with `{ user_id, follower_count }`
