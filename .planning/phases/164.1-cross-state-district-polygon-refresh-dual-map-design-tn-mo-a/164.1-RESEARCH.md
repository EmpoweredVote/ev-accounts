## Summary

This phase adds a second, parallel vintage of `essentials.geofence_boundaries` rows for 5 states' congressional districts so `/elections` can resolve 2026-enacted boundaries while the reps feed (and several supporting caches) keep resolving 2025-TIGER boundaries until a queued Jan-2027 promotion phase. Live read-only introspection against PROD confirms the schema ground truth CONTEXT.md asserted (`geofence_boundaries` unique on `(geo_id, mtfcc)`, GIST on geometry, unused text `valid_from`/`valid_to`) and, more importantly, surfaces three things CONTEXT.md's canonical refs did not fully anticipate: (1) **all** affected NATIONAL_LOWER districts in TN/AL/LA/UT/MO have `districts.mtfcc = 'G5200'` (never NULL) — this makes the *default* behavior of `electionService.ts`'s coordinate join and `getElectionsByGeoIds`'s district join **already fail-safe** against a new mtfcc value with **zero code change**, so the "opt-in" work is narrowly scoped to one query per elections path, not a sweeping audit; (2) a shared `MTFCC_DISTRICT_TYPE_GUARD` catch-all clause (`mtfcc NOT IN (known set) AND mtfcc NOT LIKE 'X%'` → matches ANY district type) exists in **three** places (`geoIdGuard.ts`, an inline duplicate in `essentialsService.ts`'s reps query, and nowhere else) and **will** silently start matching a naively-chosen new mtfcc value unless that value is explicitly added to the exclusion list in both places — this is the actual fail-dangerous trap D-01 worries about, now pinpointed to two exact code locations; (3) `essentials.geo_districts` (a **second**, mtfcc-less table with `UNIQUE(layer, geoid)`) is what actually backs `connect.user_districts` via `resolve_user_districts`/`cache_user_districts`, and it **cannot** hold a second vintage row for the same geoid — so the D-04 "no-touch" guarantee is not just a policy choice, it is a structural fact for this table (the loader must skip `geo_districts` inserts for the 5 states entirely). A fourth finding, not previously flagged anywhere in the canon: `connect.connected_profiles.congressional_geo_id` (populated once by `resolve_user_jurisdiction`, refreshed weekly by `districtStalenessService.ts`, and consumed by `getElectionsByGeoIds` on the **logged-in Connected-tier elections path**, Path 1) will **never** pick up 2026-vintage geometry because `resolve_user_jurisdiction` hardcodes `mtfcc = 'G5200'` with no catch-all — meaning Connected-tier users whose address sits in a "differential zone" will see the **old** district's race on `/elections`, not the new one, contradicting the phase's headline promise for that one user population. This needs an explicit scope decision (see Open Questions).

D-08 web research confirms official/high-confidence shapefile sources for TN (Comptroller GIS, PDF+KMZ confirmed, direct .shp unconfirmed), LA (`redist.legis.la.gov`, a confirmed downloadable `Shapefile - Act_2_(2026_RS).zip`), and UT (Utah AGRC/SGID, a confirmed live ArcGIS REST FeatureServer endpoint for "US Congress Districts 2026 to 2032"). AL's situation is more legally tangled than CONTEXT anticipated — a June 2, 2026 SCOTUS stay in *Milligan v. Allen* reinstated Alabama's 2023 legislature-drawn map (1 Black-opportunity district) **over** the interim court-ordered remedial map (2 Black-opportunity districts, currently loaded via TIGER 2024) for the 2026 cycle — this is consistent with, not contradictory to, 163-01's severity finding, but the exact GIS artifact needs confirmation from the Alabama Secretary of State's "State District Maps" page at plan time. MO's certification deadline is more precisely Aug-4 (SOS Hoskins' own statutory deadline), not ~Jul-28 (that's the *county-level* signature-certification sub-deadline) — the date-gate should be corrected.

**Primary recommendation:** Use a distinct `mtfcc` value (e.g. `'G5200V26'`) as the D-01 discriminator (not a new column) — it is a smaller diff, reuses the existing unique index and GIST index for free, and (per the live-verified schema) it costs exactly two explicit code edits (the two `MTFCC_DISTRICT_TYPE_GUARD` catch-alls) plus one new opt-in JOIN clause in `electionService.ts`'s two elections-lookup functions. Skip `geo_districts` entirely for the 5 states' imports (structurally required, not optional). Treat the `connected_profiles.congressional_geo_id` gap as an explicit scope decision before planning D-10's differential-point test, since that test must run through the live-coordinate path, not the cached Connected-tier path.

### D-01: Vintage Discriminator Mechanism — Recommendation

**Live-verified schema ground truth** (read-only introspection against PROD, 2026-07-07):

```
essentials.geofence_boundaries: UNIQUE (geo_id, mtfcc) [btree, also a duplicate non-unique
  idx with the same columns — idx_geofence_boundaries_geo_id_mtfcc — both present, redundant
  but harmless]; GIST on geometry; btree on state; valid_from/valid_to are TEXT and NULL on
  every existing row (confirmed unused).
essentials.districts: mtfcc is TEXT, nullable. For district_type='NATIONAL_LOWER': 436 of 437
  rows have mtfcc='G5200'; exactly 1 row nationwide has mtfcc=NULL (not one of the 5 affected
  states — TN/AL/LA/MO/UT all show mtfcc='G5200' on every NATIONAL_LOWER row, verified by
  direct query). [VERIFIED: live psql query against PROD]
```

**Recommendation: use a distinct `mtfcc` VALUE, not a new column.** `'G5200V26'` (or any short,
unambiguous, clearly-namespaced string under the existing `character varying` column — no schema
migration needed, the unique index `(geo_id, mtfcc)` already accepts it for free).

**Why this is fail-safe by default (verified, not assumed):**

1. `electionService.ts`'s `getElectionsByCoordinate` Part A joins `gb.geo_id = d.geo_id AND (d.mtfcc IS NULL OR d.mtfcc = '' OR gb.mtfcc = d.mtfcc)`. Since `d.mtfcc = 'G5200'` (never NULL/empty) for every affected district, this condition reduces to `gb.mtfcc = 'G5200'` — a brand-new `'G5200V26'` row will **not** match this join without a code change. [VERIFIED: read source + live schema]
2. `resolve_user_jurisdiction` (the RPC behind `connect.connected_profiles.congressional_geo_id`) explicitly enumerates `gb.mtfcc = 'G5200' AND d.district_type = 'NATIONAL_LOWER'` with **no catch-all branch** in that query at all — a new mtfcc value is invisible to it by construction. [VERIFIED: `pg_get_functiondef`]
3. `informBoundaryService.ts`'s `getBoundary`/`getBoundaryBatch` require an exact `(mtfcc, geo_id)` match passed in by the caller — no catch-all. Safe by default.

**Where it is NOT fail-safe by default — the actual risk, pinpointed:**

`essentialsService.ts`'s `getRepresentativesByAddress` (reps feed) and the shared `MTFCC_DISTRICT_TYPE_GUARD` constant in `geoIdGuard.ts` (used by `electionService.ts`'s `getElectionsByGeoIds`/`fetchDistrictRaceRows`) both end their MTFCC-to-district_type mapping with an **explicit catch-all**:

```sql
-- geoIdGuard.ts line 27 (and an inline byte-for-byte duplicate in essentialsService.ts ~line 652)
OR (gp.mtfcc NOT IN ('G5210','G5220','G5200','G4020','G4040','G4110','G4120','G5400','G5410','G5420')
    AND gp.mtfcc NOT LIKE 'X%')
```

This clause exists to let *future, not-yet-enumerated* local MTFCCs (e.g. a new city-council layer) match any district type rather than being silently dropped. A brand-new `'G5200V26'` value satisfies `NOT IN (...)` and `NOT LIKE 'X%'` — so it **would** pass this catch-all and match **any** `district_type` sharing that geo_id, in the reps feed, defeating D-01's fail-safe intent. **This is the fail-dangerous scenario D-01 describes, now pinned to two exact lines of code.**

**Required opt-in / exclusion patch (two small, explicit edits):**

1. `geoIdGuard.ts` line 27 and `essentialsService.ts`'s inline duplicate: add `'G5200V26'` to the `NOT IN (...)` list, so the new vintage marker is explicitly excluded from the "unknown MTFCC" catch-all (making its exclusion a documented decision, not an accident of naming).
2. `electionService.ts`'s `getElectionsByCoordinate` Part A geofence join, and `fetchDistrictRaceRows` (used by `getElectionsByGeoIds`): add an explicit vintage-preference join so the 5 affected states' NATIONAL_LOWER geometry resolves against `'G5200V26'` when it exists, else `'G5200'`. Suggested shape (LATERAL, avoids a second full table scan):

```sql
-- electionService.ts getElectionsByCoordinate Part A — REPLACE the plain JOIN with:
JOIN essentials.offices o ON o.id = r.office_id
JOIN essentials.districts d ON d.id = o.district_id
JOIN LATERAL (
  SELECT geometry FROM essentials.geofence_boundaries gbv
   WHERE gbv.geo_id = d.geo_id AND gbv.mtfcc = 'G5200V26'
     AND d.district_type = 'NATIONAL_LOWER'
  UNION ALL
  SELECT geometry FROM essentials.geofence_boundaries gbo
   WHERE gbo.geo_id = d.geo_id
     AND (d.mtfcc IS NULL OR d.mtfcc = '' OR gbo.mtfcc = d.mtfcc)
     AND NOT EXISTS (
       SELECT 1 FROM essentials.geofence_boundaries x
        WHERE x.geo_id = d.geo_id AND x.mtfcc = 'G5200V26'
     )
  LIMIT 1
) gb ON true
WHERE gb.geometry IS NOT NULL
  AND public.ST_Covers(gb.geometry, public.ST_SetSRID(public.ST_MakePoint($1::float8, $2::float8), 4326))
  AND ${ELECTION_VISIBILITY_WINDOW}
```

This guarantees: any of the other 33 states (no `'G5200V26'` row exists for their geo_ids) fall straight through to the unchanged `'G5200'` branch — zero blast radius outside TN/AL/LA/UT(/MO). Only geo_ids that actually got a new-vintage row prefer it.

## Import Pipeline

**Recommendation: clone-and-adapt `load-national-house-districts.ts`'s per-state pattern, NOT the generalized `load-state-tiger-boundaries.ts` allowlist loader.**

Rationale: `load-state-tiger-boundaries.ts` (Phase 130) is purpose-built around TIGER's fixed, well-known column names and TIGER's per-state download URL convention (`STATE_LAYER_ALLOWLIST`, `insertDistrictIfMissing`). The 5 states' 2026 shapefiles come from 4-5 **different, non-TIGER sources** with non-uniform column schemas (LA's Act 2 shapefile, TN's Comptroller KMZ, UT's ArcGIS FeatureServer JSON, AL's SOS shapefile) — forcing them through the TIGER-shaped allowlist loader would require as much per-state special-casing as a fresh clone, with the added risk of perturbing the allowlist's existing CA/TX/UT(TIGER)/IN/MA/ME/OR/MD/VA/NV/DC configurations (UT is ALREADY in that allowlist for a completely different purpose — sub-state layers like `sldu`/`sldl`/`unsd` — collision risk if reused carelessly).

Instead, clone `load-national-house-districts.ts`'s three reusable primitives per state:
1. `resolveColumn()` — column-name resolver with a loud throw on total miss (generalizes trivially to any shapefile's DBF/property schema).
2. `downloadWithRedirects()` / `extractZip()` / `streamShapefile()` — verbatim-reusable HTTP/zip/shapefile-streaming helpers (already marked "copied verbatim" in the source file's own comments, meaning they're already treated as a shared utility, just not extracted into a shared module yet — an easy `import` if the planner wants to de-duplicate).
3. The `ON CONFLICT (geo_id, mtfcc) DO NOTHING` insert into `geofence_boundaries` — **change only the `MTFCC` constant** from `'G5200'` to `'G5200V26'` (or whichever value D-01 settles on) and the `SOURCE` constant to something like `'state_gis_2026'` per state, recording per-state provenance in the `source` text column (currently populated as `'census_tiger_2024'` for the old-vintage rows — a natural place to record `'tn_comptroller_2026'`, `'la_legis_2026'`, `'ut_agrc_2026'`, `'al_sos_2026'` for auditability).

**CRITICAL — the `geo_districts` insert block MUST be dropped entirely from the 2026-vintage import scripts.** `load-national-house-districts.ts`'s existing script inserts into BOTH `geofence_boundaries` (mtfcc-keyed, supports parallel vintages) AND `geo_districts` (`UNIQUE(layer, geoid)`, no vintage column — feeds `resolve_user_districts`/`cache_user_districts`/`connect.user_districts`, the D-04 no-touch surface). If a cloned import script keeps the `geo_districts` insert unmodified, it will either (a) silently no-op via `ON CONFLICT DO NOTHING` (harmless but pointless — the row already exists from the TIGER 2024 load), or worse (b) if anyone "fixes" the `ON CONFLICT` to `DO UPDATE` thinking it needs refreshing, it will **overwrite the reps-feed cache source with 2026 geometry**, silently breaking D-04. Recommend the per-state 2026 import scripts **only ever write to `geofence_boundaries`**, and the D-04 gate assertion should include an explicit `SELECT COUNT(*), md5(...)` (or simpler: a row-count + `imported_at`/`updated_at`-max check) on `essentials.geo_districts WHERE layer='us_house' AND geoid LIKE '{state_fips}%'` pre/post, alongside the existing `essentials.offices` byte-identical assertion.

## D-10: Verify Bar Mechanics

The 3-layer bar extends the exact harness already proven in `163-coordinate-smoke.ts` (read in full this session) and its accompanying `163-verify.sql` (11 PASS-block pattern, documented in `163-11-SUMMARY.md`). Concretely:

**Layer 1 — Topology sanity (new SQL, no precedent to clone from — this phase is the first to need it):**
```sql
-- Per state: does the state's 2026-vintage districts tile the state boundary?
SELECT s.state,
       ST_Area(ST_Difference(state_outline.geometry, ST_Union(gb.geometry))) AS uncovered_area,
       ST_Area(ST_Union(gb.geometry)) AS covered_area
FROM essentials.geofence_boundaries gb
JOIN essentials.geofence_boundaries state_outline ON state_outline.mtfcc = 'G4000' AND state_outline.state = gb.state
WHERE gb.mtfcc = 'G5200V26' AND gb.state = '{FIPS}'
GROUP BY s.state, state_outline.geometry;
-- Per-district area sanity: each district's area should be within an order of magnitude of
-- its OLD-vintage counterpart (catches a badly-mis-imported or truncated polygon)
SELECT old.geo_id, ST_Area(old.geometry) AS old_area, ST_Area(new.geometry) AS new_area,
       ST_Area(new.geometry) / NULLIF(ST_Area(old.geometry), 0) AS ratio
FROM essentials.geofence_boundaries old
JOIN essentials.geofence_boundaries new ON new.geo_id = old.geo_id AND new.mtfcc = 'G5200V26'
WHERE old.mtfcc = 'G5200' AND old.state = '{FIPS}';
```
(`G4000` state-outline mtfcc is already used elsewhere in the codebase — `readrankService.ts`'s `MTFCC_SCOPE` map — confirming a state-boundary layer already exists to diff against.)

**Layer 2 — Per-district positive anchor coordinate:** identical shape to `163-coordinate-smoke.ts`'s `SAMPLES` loop (lines 76-148 of that file) — pick one interior point per district (e.g. `ST_PointOnSurface` of the NEW-vintage geometry, exactly as the existing script does for old-vintage), assert `getElectionsByCoordinate`-equivalent SQL returns exactly 1 race with the expected candidate count. **Layer 3 — Differential point (new pattern, the actual dual-map proof):** requires a coordinate whose OLD-vintage district assignment differs from its NEW-vintage assignment. This cannot be chosen a priori from CONTEXT alone — it requires `ST_Difference`/`ST_SymDifference` between each state's OLD and NEW geometries once both are imported, to find a point that changed sides. Recommended query pattern to *discover* candidate differential points once the 2026 shapefiles are loaded:
```sql
-- Find a point in NEW district A that falls in OLD district B (A != B) — the genuine differential zone
SELECT new.geo_id AS new_geo_id, old.geo_id AS old_geo_id,
       ST_X(ST_PointOnSurface(ST_Intersection(new.geometry, ST_Difference(new.geometry, old_same.geometry)))) AS lng,
       ST_Y(ST_PointOnSurface(ST_Intersection(new.geometry, ST_Difference(new.geometry, old_same.geometry)))) AS lat
FROM essentials.geofence_boundaries new
JOIN essentials.geofence_boundaries old ON old.mtfcc = 'G5200' AND old.state = new.state
JOIN essentials.geofence_boundaries old_same ON old_same.geo_id = new.geo_id AND old_same.mtfcc = 'G5200'
WHERE new.mtfcc = 'G5200V26' AND old.geo_id != new.geo_id
  AND ST_Intersects(new.geometry, old.geometry)
  AND ST_Area(ST_Intersection(new.geometry, old.geometry)) > 1e-9;
-- Then assert: getElectionsByCoordinate(lat,lng) surfaces new.geo_id's race, AND
--              getRepresentativesByAddress-equivalent-by-coordinate surfaces old.geo_id's rep.
```

## Common Pitfalls

### Pitfall 1: The shared MTFCC catch-all silently adopts the new vintage marker
**What goes wrong:** A new `mtfcc` value chosen for 2026-vintage rows passes `essentialsService.ts`'s and `geoIdGuard.ts`'s "unknown MTFCC matches any district type" fallback clause, causing the reps feed (and `getElectionsByGeoIds`, if ever fed a live-derived pair with the new mtfcc) to start resolving on 2026 geometry for districts it should not.
**Why it happens:** Both catch-alls were written to gracefully accept *future, not-yet-enumerated* local layers — they were not designed with an intentionally-withheld vintage marker in mind.
**How to avoid:** Add the chosen mtfcc value to both catch-all exclusion lists (`geoIdGuard.ts` line 27, `essentialsService.ts`'s inline duplicate ~line 652) as an explicit, commented decision — not an accident of the string not colliding with the enumerated set.
**Warning signs:** Reps-feed spot-checks in a differential zone suddenly return the NEW district's representative info (there won't be one — `essentials.offices` was never re-keyed — so it would actually surface an empty/wrong join, likely 0 rows or a stale office, not a clean failure).

### Pitfall 2: `geo_districts` insert accidentally overwrites the D-04 no-touch surface
**What goes wrong:** A cloned import script keeps `load-national-house-districts.ts`'s `geo_districts` INSERT block; if anyone changes its `ON CONFLICT DO NOTHING` to `DO UPDATE` (e.g., "to keep it fresh"), it silently promotes `connect.user_districts`'s resolution source to 2026 geometry for the 5 states, breaking D-04 without any error.
**Why it happens:** The two-table write pattern (`geofence_boundaries` + `geo_districts`) is baked into the precedent loader as a single atomic unit; it's easy to copy both INSERTs without noticing `geo_districts` has no vintage column at all.
**How to avoid:** Drop the `geo_districts` INSERT entirely from the 2026-vintage import scripts; add an explicit pre/post row-count (or `MAX(id)`) assertion on `essentials.geo_districts WHERE layer='us_house' AND geoid LIKE '{fips}%'` to the phase gate, alongside the `essentials.offices` byte-identical check.
**Warning signs:** `connect.user_districts`/`/api/account/districts` for a test Connected user in a differential zone suddenly returns the NEW district instead of the OLD one.

### Pitfall 3: `connected_profiles.congressional_geo_id` breaks the differential-point promise for logged-in users
**What goes wrong:** D-10's Layer 3 differential-point test, if run against a **Connected-tier logged-in session** (rather than the uncached address-lookup path), will show the OLD district's race on `/elections`, not the NEW one — appearing to fail the dual-map's core promise.
**Why it happens:** `getElectionsByGeoIds` (the Path 1 elections lookup for Connected users) reads a STORED `congressional_geo_id` from `connect.connected_profiles`, populated once by `resolve_user_jurisdiction` (hardcoded to `mtfcc='G5200'`, never re-derives from live geometry) and refreshed weekly by `districtStalenessService.ts` — which calls the SAME hardcoded RPC, so it will never detect the 2026 boundaries exist.
**How to avoid:** Run the D-10 Layer 3 test against the **uncached, live** `getElectionsByCoordinate` path only (the guest/first-lookup `/api/elections?address=` route) — this is genuinely live `ST_Covers`, matching D-04's claim. Do NOT test via a Connected-tier session unless the planner has made an explicit decision about this gap (see Open Questions).
**Warning signs:** A differential-point smoke test that "sometimes passes, sometimes fails" depending on which route/auth state it's run through — that's this exact bug, not test flakiness.

### Pitfall 4: AL's shapefile is not the map currently in the DB — verify direction before importing
**What goes wrong:** Assuming "AL's 2026 map" means importing a HIGHER-BVAP map (matching the popular narrative of "new majority-Black district") when the actual 2026 change is the OPPOSITE direction — SCOTUS reinstated the LOWER-BVAP 2023 legislature map over the interim court-ordered 2-Black-district map that's currently loaded in the DB (via TIGER 2024).
**Why it happens:** The AL redistricting saga has multiple maps in play (2021 original, 2023 legislature remap, 2023 court-ordered remedial map, and now the SCOTUS-reinstated 2023 legislature remap) and news coverage doesn't always disambiguate which one is "current" at any given moment.
**How to avoid:** Before importing, confirm via the Alabama Secretary of State's official map page which exact map is certified for the 2026 ballot, and cross-check its AL-2 BVAP figure against 163-01's audit (~39.9%, the "severe" new figure) — if the sourced shapefile's AL-2 BVAP is instead ~48.7% (the OLD figure), the wrong map was downloaded.
**Warning signs:** Post-import topology-sanity (Layer 1) passes but the un-withhold differential-point test for AL-2 doesn't show the expected shift.

### Pitfall 5: MO's date-gate trigger date is Aug-4, not ~Jul-28
**What goes wrong:** Starting the MO plan on Jul-28 based on CONTEXT's estimate, before SOS Hoskins' actual Aug-4 certification decision, risks importing/un-withholding against a map that could still legally revert.
**Why it happens:** Jul-27 is the county-clerk-to-SOS signature sub-certification deadline; Hoskins' own statutory certification window explicitly extends through Aug-4 per his own public statements (sourced 2026-06-01).
**How to avoid:** Update D-05's re-entry date to ≥ 2026-08-04 (or re-verify the exact date at plan-authoring time — MO's legal timeline has already shifted once between the 162-01 audit and this research pass).
**Warning signs:** N/A — this is a scheduling correction, not a runtime symptom.

## Open Questions

1. **Should `connected_profiles.congressional_geo_id` staleness for differential-zone Connected users be an accepted, documented scope limitation (parallel to the reps-feed/offices tradeoff), or does it need an explicit fix in this phase?**
   - What we know: `getElectionsByGeoIds` (Path 1, used by logged-in Connected-tier users' `/elections` lookups) reads a cached `congressional_geo_id` that can never reflect 2026 geometry (the RPC behind it hardcodes `mtfcc='G5200'` with no catch-all, and a weekly cron re-confirms rather than corrects this). For non-differential-zone users this is invisible (same geo_id both vintages); for differential-zone users (the exact population D-10's Layer 3 test is designed to prove) it means their elections feed shows the OLD district's race.
   - What's unclear: whether this is an acceptable, D-04-consistent tradeoff (same philosophy as "reps feed / offices stay old until Jan-2027") extended to one more surface CONTEXT didn't explicitly name, or whether the phase's headline promise ("elections resolves on 2026 boundaries") is meant to hold for ALL users including Connected-tier, in which case a small additional fix is needed (e.g., Path 1 could re-derive live for NATIONAL_LOWER specifically, or fall back to a live coordinate check when the cached geo_id's state is one of the 5 affected states).
   - Recommendation: treat as an accepted, documented limitation for 164.1 (matches D-04's spirit, smallest diff, no touch to `connected_profiles`/`resolve_user_jurisdiction`), explicitly note it in the phase's summary/README as a known gap closed by the Jan-2027 promotion phase, and make sure D-10's differential-point test is run through the uncached path only (Pitfall 3) so the gate doesn't accidentally fail on a known, accepted limitation.

2. **Exact differential-point coordinates cannot be chosen until the 2026 shapefiles are actually imported.**
   - What we know: the SQL pattern to discover them (comparing `ST_Difference`/`ST_Intersection` of OLD vs NEW geometry per state) is specified above (D-10 Layer 3).
   - What's unclear: which specific districts in each state actually have a differential zone large enough to pick a stable, non-edge-case test point (LA-4's ~20-22%-moved borderline flag from 163-01 suggests LA is a good candidate; TN's 5-of-9 severe set suggests TN has several options).
   - Recommendation: treat this as a Wave-0/first-task item in the execution plan (compute after import, before D-10 gate authoring), not a research-time deliverable — it's mechanically dependent on having the actual polygons in hand.

3. **AL's exact GIS artifact (shapefile vs geojson vs KML) from the Secretary of State's page.**
   - What we know: the page is described as hosting shape files per a search snippet; a direct fetch attempt failed on a certificate error this session (a proxy/browser fetch, not `curl`, may succeed at plan time — same pattern 163-01 documented for other AL sources).
   - What's unclear: exact file format and URL.
   - Recommendation: confirm via `curl`/Playwright/RDH at plan-authoring time; RDH is an explicit, D-08-approved fallback if the state source proves unreachable.
