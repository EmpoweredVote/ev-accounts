<objective>
Patch the existing AuthInput component to accept an optional `inputClassName?: string` prop that is appended to the internal base className string of the rendered `<input>` element.

Purpose: Phase 61's signup page restyle needs the invite-code field to render in `font-mono tracking-wider` so codes like `XXXX-XXXX` stay readable. The current AuthInput spreads `inputProps` BEFORE setting `className` explicitly, so any `inputProps.className` from the consumer is silently overridden. Without this patch, the SignupPage restyle (Plan 04) cannot preserve invite-code mono styling, and any future field that needs custom input classes will hit the same wall.

Output: AuthInput.tsx accepts a clean `inputClassName` prop. Existing callers keep working with no changes. New callers can opt in to extra utility classes on the input element.
</objective>

3. Update the rendered `<input>` className to append `inputClassName`. Use a template literal and `.trim()` so an empty string does not produce a trailing space:
   ```tsx
   className={`w-full bg-gray-800 border ${borderClass} rounded-xl px-4 py-3 text-white placeholder-gray-500 focus:outline-none focus:ring-2 text-base ${inputClassName}`.trim()}
   ```
   Keep the existing `placeholder-gray-500` and `focus:outline-none focus:ring-2 text-base` ordering — do not rearrange utilities.
4. Do NOT change the `{...inputProps}` spread or its position. The spread stays first; the explicit `className` still wins. This preserves the existing override-protection behavior for `type`, `value`, `onChange`, `className`, etc.

Why this approach (and not merging via inputProps.className): Merging `inputProps.className` would require changing the spread order, which would let consumers accidentally override `type`/`value`/`onChange`. A dedicated `inputClassName` prop is the safer, more explicit API and keeps the existing prop contract intact.
