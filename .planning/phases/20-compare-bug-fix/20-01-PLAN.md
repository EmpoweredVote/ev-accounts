Fix the double overlay bug in RadarChartCore.jsx. There are two root causes to address:

**Root cause 1: Compare polygon points are calculated using wrong spoke angles.**
The compare polygon (line 54) iterates `Object.entries(compareData)` using its own `index` for angle calculation, but the angles must align with the USER's data spokes. If `compareData` has different key order than `data`, the compare shape renders at wrong positions.

Fix: Instead of iterating `compareData` independently, iterate `spokes` (derived from `data`) and look up each short_title in `compareData`. This guarantees the compare polygon vertices align exactly with the user polygon vertices:

```javascript
let comparePoints = null;
if (Object.keys(compareData).length) {
  const cpts = spokes.map(([shortTitle], index) => {
    const value = compareData[shortTitle] ?? 0;
    const topic = topics.find((t) => t.short_title === shortTitle);
    const max = topic?.stances?.length || 10;
    const pct = Math.min((value / max) * 10, 10);
    const angle = (2 * Math.PI * index) / numSpokes;
    const adjusted =
      value === 0 ? 0 : invertedSpokes[shortTitle] ? 11 - pct : pct;
    const r = (adjusted / 10) * radius;
    const x = centerX + r * Math.sin(angle);
    const y = centerY - r * Math.cos(angle);
    return `${x},${y}`;
  });
  comparePoints = cpts.join(" ");
}
```

**Root cause 2: compareSpring renders stale polygon when comparePoints is null.**
The `useSpring` for compare data (line 71) receives `to: { points: comparePoints }` where `comparePoints` can be `null`. When the spring has a previous animated value and `comparePoints` is `null`, the animated polygon may briefly render a stale shape during transitions. Also, when `comparePoints` transitions from null to a valid value, the spring interpolates from whatever its previous state was.

Fix: When `comparePoints` is null, pass `immediate: true` to the compareSpring so it doesn't animate from stale values. Also, conditionally render the compare polygon ONLY when `comparePoints` is truthy (already done on line 208, but the spring itself should be clean):

```javascript
const compareSpring = useSpring({
  to: { points: comparePoints || "" },
  immediate: countChanged || !comparePoints,
  reset: countChanged,
  config: { tension: 300, friction: 30 },
});
```

**Root cause 3: Static and animated polygons can briefly coexist.**
The ternary on line 208-228 switches between static `<polygon>` (when countChanged) and `<animated.polygon>` (otherwise). When countChanged flips between renders, React may briefly show both. This is a minor contributor but the fix is straightforward -- ensure only one element renders by using `key` to force React reconciliation:

For the compare polygon section, ensure the conditional branches produce clean elements. The existing ternary is fine structurally, but add a key to both:

```jsx
{comparePoints ? (
  countChanged ? (
    <polygon
      key="compare-static"
      points={comparePoints}
      style={{
        fill: "rgba(89, 176, 196, 0.3)",
        stroke: "rgb(89, 176, 196)",
        strokeWidth: 2,
      }}
    />
  ) : (
    <animated.polygon
      key="compare-animated"
      points={compareSpring.points}
      style={{
        fill: "rgba(89, 176, 196, 0.3)",
        stroke: "rgb(89, 176, 196)",
        strokeWidth: 2,
      }}
    />
  )
) : null}
```

Also apply the same key pattern to the user polygon (lines 188-206) for consistency:
- `key="user-static"` for the static polygon
- `key="user-animated"` for the animated polygon

The useEffect at ~line 521 that builds compareAnswers depends on `[comparePol, selectedTopics, topics, setCompareAnswers]`. The `topics` dependency causes the effect to re-fire every time topic metadata changes (which happens during admin edits, initial load, etc.), even though the topic metadata is only needed for the short_title lookup. Since `topics` is already accessible via the `topicsRef` pattern established earlier in the file (line 411-412), use that pattern here too.

Change the dependency array from:
```javascript
}, [comparePol, selectedTopics, topics, setCompareAnswers]);
```
to:
```javascript
}, [comparePol, selectedTopics, setCompareAnswers]);
```

And inside the effect, replace `topics.find(...)` with `topicsRef.current.find(...)`:
```javascript
const mapped = selectedTopics
  .map((id) => {
    const a = allAnswers.find((x) => x.topic_id === id);
    const t = topicsRef.current.find((tt) => tt.id === id);

    return [t.short_title, a ? a.value : 0];
  })
  .filter(Boolean);
```

This mirrors the exact same pattern used for the user answer fetch effect at line 415 which already uses `topicsRef` to avoid re-firing on topic metadata changes.
