**IMPORTANT: Read 41-01-SUMMARY.md first.** It contains the exact table inventory, row counts, FK gap analysis results, Trivia connection model decision, and FK resolution strategy. All details below must be adapted based on Plan 01 findings.

**Step A: Dump schemas from source**

The source database is the EV-Backend Supabase project. Get the direct connection string from the Supabase MCP config or ask the user.

NOTE: If validation_quests is on a SEPARATE Supabase project from EV-Backend (discovered in Plan 01), use that project's DATABASE_URL for the VQ dump.

```bash
# Dump validation_quests
pg_dump \
  --schema=validation_quests \
  --no-owner \
  --no-privileges \
  --no-acl \
  -f /tmp/vq-export.sql \
  "$SOURCE_DATABASE_URL"

# Dump trivia
pg_dump \
  --schema=trivia \
  --no-owner \
  --no-privileges \
  --no-acl \
  -f /tmp/trivia-export.sql \
  "$SOURCE_DATABASE_URL"
```

**Step B: Review dump files before restore**

Before restoring, inspect both dump files for:
1. `SET search_path` directives that could cause tables to land in wrong schema -- remove or comment out if found
2. `CREATE EXTENSION` statements for extensions that already exist in ev-accounts -- remove or wrap in `CREATE EXTENSION IF NOT EXISTS`
3. FK constraints referencing external schemas (found in Plan 01 Task 1 query 7) -- if any FK references a table that doesn't exist in ev-accounts (e.g., EV-Backend's `public.politicians`), either:
   - Remove the constraint from the dump and re-add it after FK reconciliation
   - Or use `--disable-triggers` on restore to defer FK checks
4. Role-specific GRANT statements that slipped through `--no-privileges` -- remove any grants to roles that don't exist in ev-accounts

**Step C: Restore into ev-accounts**

Get the ev-accounts direct connection string (port 5432, not pooler).

```bash
psql "$EV_ACCOUNTS_DATABASE_URL" < /tmp/vq-export.sql
psql "$EV_ACCOUNTS_DATABASE_URL" < /tmp/trivia-export.sql
```

If restore errors on FK constraints for trivia, restore structure first (`pg_dump --schema-only`), resolve FKs, then restore data (`pg_dump --data-only`).

**Step D: Verify row counts**

Run COUNT(*) on every table in both schemas on ev-accounts. Compare against the baseline from 41-01-SUMMARY.md. Every count must match exactly. If any mismatch, investigate before proceeding.

**Step E: Resolve trivia FK gaps**

Based on the FK gap resolution strategy decided in Plan 01:
- If inserting missing politicians: INSERT into essentials.politicians with minimal required fields (name, id from source)
- If nulling unmatched FKs: UPDATE the trivia table SET politician_id = NULL WHERE politician_id NOT IN (SELECT id FROM essentials.politicians)
- Log the exact rows affected (IDs and count)

If Plan 01 found zero FK gaps, skip this step.

**Step F: Record migration**

Create `supabase/migrations/20260322000051_phase41_vq_trivia_restore.sql` as a documentation migration. This file should contain:
- Comment block explaining the pg_dump/restore process (dates, source, target)
- The FK resolution SQL that was executed (if any)
- This file is NOT meant to be re-run -- it documents what was done manually

Add this migration to `backend/src/lib/applyMigrations.ts` in the migrations array.

**Read 41-01-SUMMARY.md for the Trivia connection model decision.**

Execute the following SQL via Supabase MCP `execute_sql` against ev-accounts:

```sql
-- vq_service role (always created)
CREATE ROLE vq_service WITH LOGIN PASSWORD '<generate-a-strong-random-password>';
GRANT USAGE ON SCHEMA validation_quests TO vq_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA validation_quests TO vq_service;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA validation_quests TO vq_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA validation_quests GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO vq_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA validation_quests GRANT USAGE, SELECT ON SEQUENCES TO vq_service;
ALTER ROLE vq_service SET search_path = validation_quests;
ALTER ROLE vq_service BYPASSRLS;
```

Generate a strong password (32+ chars, alphanumeric). Record it securely -- user will need it for Render env var update.

**If Trivia uses DATABASE_URL (from Plan 01 decision):**
```sql
CREATE ROLE trivia_service WITH LOGIN PASSWORD '<generate-another-strong-password>';

GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA trivia TO trivia_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA trivia GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO trivia_service;
ALTER DEFAULT PRIVILEGES IN SCHEMA trivia GRANT USAGE, SELECT ON SEQUENCES TO trivia_service;
```
