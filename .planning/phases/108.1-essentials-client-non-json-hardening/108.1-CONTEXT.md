# Phase 108.1 — Essentials client: wrap non-JSON 200 responses

## Why this phase exists

While running Phase 108 Test 1 (live endpoint smoke) against `accounts.empowered.vote`, the production host returned HTTP 200 with `Content-Type: text/html` (the admin SPA catch-all, because the real backend was at `api.empowered.vote` and Phase 107 hadn't shipped yet). `CouncilScribe/src/essentials_client.py::fetch_body_roster` called `resp.json()` unconditionally, which let a raw `requests.exceptions.JSONDecodeError` bubble up the stack instead of wrapping it in `EssentialsClientError`.

This is a minor robustness gap: the error envelope contract promised by `EssentialsClientError` (clean stderr message, non-zero exit, existing cache byte-identical) only holds for network-layer failures, not for "HTTP 200 with wrong content-type". It's outside the explicit Phase 108 acceptance truths, but it surfaced in real debugging and made the cause non-obvious.

## Scope (tight)

Single file: `CouncilScribe/src/essentials_client.py`.

Single function: `fetch_body_roster`.

Change: wrap `resp.json()` in a try/except that catches `requests.exceptions.JSONDecodeError` (and optionally validates `Content-Type` starts with `application/json`) and raises `EssentialsClientError(f"Non-JSON response from {url}: {body[:200]}")`.

Plus one unit test in `tests/test_essentials_client.py` that patches `requests.get` to return HTTP 200 with `text/html` and asserts `EssentialsClientError` is raised with a message containing a snippet of the body.

## Out of scope

- Retry logic on transient errors
- Content-Type strict validation (advisory — we'll catch the parse error, which is sufficient)
- Any changes to `refresh_roster.py` CLI (it already catches `EssentialsClientError` and exits non-zero with stderr — no change needed once the client wraps correctly)
- Any changes to `roster.py` or alias_gen.py

## Evidence of the bug

From Phase 108's 108-HUMAN-UAT.md (G2):

> When the endpoint returns HTTP 200 with non-JSON, `fetch_body_roster` lets `requests.exceptions.JSONDecodeError` escape instead of wrapping it in `EssentialsClientError`.

Observed traceback during Test 1 attempt against `accounts.empowered.vote`:

```
requests.exceptions.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  File "CouncilScribe/src/essentials_client.py", line 114, in fetch_body_roster
    return resp.json()
```

## Requirements

- **CSROSTER-03 (hardening)** — Client error envelope must cover all "response unusable" cases, not only transport-layer failures. An HTTP 200 with non-JSON body is just as "unusable" as a connection refusal.
