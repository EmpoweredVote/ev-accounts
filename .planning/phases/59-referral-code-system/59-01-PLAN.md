**RPC 1: `connect.generate_invite_code_if_allowed(p_user_id UUID)`**

Returns TABLE (ok BOOLEAN, code TEXT, error TEXT, active_count INT, cap INT).

Logic (all inside a single function body):
1. `PERFORM pg_advisory_xact_lock(hashtext(p_user_id::text));` — prevent concurrent double-generation (same pattern as `award_xp`)
2. Read `current_level` and `invite_cap_override` from `connect.connected_profiles WHERE user_id = p_user_id` using `FOR UPDATE`
3. If no row found, RETURN `(false, NULL, 'NOT_CONNECTED', 0, 0)`
4. Compute level-based cap via `connect.get_invite_cap_for_level(v_level)`
5. Handle unlimited: if `v_override = -1`, set `v_effective_cap := 2147483647` (skip GREATEST)
6. Otherwise: `v_effective_cap := GREATEST(v_level_cap, COALESCE(v_override, 0))`
7. Count active invitees using the canonical query:
   ```sql
   SELECT COUNT(*)::int INTO v_active_count
   FROM connect.invite_chains ic
   JOIN connect.invite_codes code ON code.id = ic.invite_code_id
   JOIN connect.connected_profiles invitee ON invitee.user_id = ic.invitee_id
   WHERE ic.inviter_id = p_user_id
     AND code.is_claimed = true
     AND invitee.current_level < 2
     AND NOT (
       ic.slot_locked_until IS NOT NULL
       AND ic.slot_locked_until < now()
       AND invitee.account_standing = 'active'
     );
   ```
   **What this counts:** All claimed invitees below level 2 (not graduated), EXCLUDING those whose lock has expired AND who are back to active standing. In detail:
   - Invitee below level 2, no lock, active standing -> COUNTS (active invitee consuming a slot)
   - Invitee below level 2, lock still active (future), suspended -> COUNTS (locked slot consuming cap)
   - Invitee below level 2, lock expired (past), active standing -> EXCLUDED (slot freed: lock expired AND invitee reinstated)
   - Invitee below level 2, lock expired (past), still suspended -> COUNTS (lock expired but invitee still suspended, slot NOT freed)
   - Invitee at level 2+ (graduated) -> EXCLUDED by `current_level < 2` filter
   This is the single source of truth for active invitee counting. The same logic is used by `get_my_invitees` below (via `active_count` output column).

8. If `v_active_count >= v_effective_cap`, RETURN `(false, NULL, 'CAP_REACHED', v_active_count, v_effective_cap)`
9. Generate code: use unqualified `gen_random_bytes(8)` — same pattern as the existing `connect.gen_referral_code` function in `20260318000001_referral_codes.sql` which also uses `SET search_path = ''` with unqualified `gen_random_bytes`. Map to charset `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, format as `XXXX-XXXX`. Include collision retry (up to 3 attempts).
10. INSERT into `connect.invite_codes (code, created_by, expires_at)` with `expires_at = now() + interval '30 days'`
11. RETURN `(true, v_code, NULL, v_active_count, v_effective_cap)`

SECURITY DEFINER, SET search_path = ''. All table refs fully qualified.

**RPC 2: `connect.get_my_invitees(p_user_id UUID)`**

Returns TABLE (invitee_id UUID, display_name TEXT, account_standing TEXT, current_level INT, graduated BOOLEAN, slot_locked_until TIMESTAMPTZ, claimed_at TIMESTAMPTZ, active_count INT, effective_cap INT).

Logic:
1. Compute effective cap for this user (same logic as generate RPC):
   - Read `current_level` and `invite_cap_override` from `connect.connected_profiles WHERE user_id = p_user_id`
   - If unlimited (-1): effective_cap = 2147483647
   - Otherwise: `GREATEST(connect.get_invite_cap_for_level(v_level), COALESCE(v_override, 0))`
   - Store in `v_effective_cap`

2. Count active invitees using the SAME canonical query as `generate_invite_code_if_allowed` (copy it exactly — same JOINs, same WHERE, same NOT(...) exclusion). Store in `v_active_count`.

3. Return all claimed invitees (not just active — include graduated and lock-expired for the complete list):
   ```sql
   RETURN QUERY
   SELECT ic.invitee_id,
          u.display_name,
          invitee.account_standing,
          invitee.current_level,
          (invitee.current_level >= 2) AS graduated,
          ic.slot_locked_until,
          code.claimed_at,
          v_active_count AS active_count,
          v_effective_cap AS effective_cap
   FROM connect.invite_chains ic
   JOIN connect.invite_codes code ON code.id = ic.invite_code_id
   JOIN connect.connected_profiles invitee ON invitee.user_id = ic.invitee_id
   JOIN public.users u ON u.id = ic.invitee_id
   WHERE ic.inviter_id = p_user_id AND code.is_claimed = true
   ORDER BY code.claimed_at DESC;
   ```
   The `active_count` and `effective_cap` columns are repeated on every row (same value). This is the single source of truth — the backend reads these from the RPC output, never computes them in JavaScript.

SECURITY DEFINER, SET search_path = ''.

**RPC 3: `connect.sanction_invitee(p_invitee_id UUID, p_tr_delta NUMERIC DEFAULT -0.25)`**

Returns VOID.

Note on p_tr_delta: Phase 59 uses a flat -0.25 penalty for all sanctions. Severity-scaled TR penalties are deferred until the sanctioning system exposes a severity field/category (see CONTEXT.md Deferred Ideas). The `p_tr_delta` parameter exists so future phases can pass severity-appropriate values without changing the RPC signature.

Logic:
1. Find inviter via `connect.invite_chains WHERE invitee_id = p_invitee_id` (may be NULL if admin-created invite)
2. If no inviter found, RETURN (no accountability chain)
3. Lock the slot: `UPDATE connect.invite_chains SET slot_locked_until = now() + interval '60 days' WHERE invitee_id = p_invitee_id AND inviter_id = v_inviter_id`
4. Adjust TR inline (NOT via nested RPC — v1.4 pattern): 
   ```sql
   UPDATE connect.connected_profiles
   SET tolerance_rating = GREATEST(0.00, COALESCE(tolerance_rating, 1.00) + p_tr_delta),
       updated_at = now()
   WHERE user_id = v_inviter_id;
   ```
5. Check if TR hit 0 — if so, auto-suspend:
   ```sql
   IF v_new_tr <= 0.00 THEN
     UPDATE connect.connected_profiles SET account_standing = 'suspended' WHERE user_id = v_inviter_id;
   END IF;
   ```
6. Notify inviter using `INSERT INTO public.notifications (user_id, type, payload)`:
   ```sql
   INSERT INTO public.notifications (user_id, type, payload)
   VALUES (v_inviter_id, 'invitee_sanctioned', jsonb_build_object(
     'invitee_id', p_invitee_id,
     'slot_locked_until', (now() + interval '60 days')::text,
     'tr_impact', p_tr_delta
   ));
   ```

SECURITY DEFINER, SET search_path = ''. Do NOT call `adjust_inviter_tolerance_rating` (that writes to legacy `notification_events` table — would cause double-notification).
