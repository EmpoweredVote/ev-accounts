**Migration 007: RLS for public schema (with split visibility)**
Per CONTEXT.md locked decision: "public.users: non-owners see display_name, avatar, and tier-derived fields; NOT email, account_standing, created_at, or internal fields."

Implementation:
- `public.users`: ENABLE RLS. Owner-only SELECT policy: `USING ((select auth.uid()) = id AND deleted_at IS NULL)`. No INSERT/UPDATE/DELETE for non-service-role. This means only the owner can query `public.users` directly.
- Create a **view** `public.users_public` that projects ONLY safe columns for cross-user reads:
  ```sql
  CREATE VIEW public.users_public AS
    SELECT id, display_name, avatar_url
    FROM public.users
    WHERE deleted_at IS NULL;
  ```
- Enable RLS on `public.users_public`. Add a SELECT policy for `authenticated` role: `USING (true)` -- any authenticated user can read the public view columns for any non-deleted user.
- `public.user_roles`: ENABLE RLS. No policies for non-service-role (admin only).
- `public.admin_audit_log`: ENABLE RLS. No policies for non-service-role (admin only, append-only).

IMPORTANT: The `users_public` view intentionally excludes: `email` (from auth.users), `account_standing` (internal), `created_at` (internal), `deleted_at` (internal), `tolerance_rating` (internal), `legal_name` (internal). Future phases that need to read another user's display_name must query `public.users_public`, NOT `public.users`.

**Migration 008: RLS for connect schema (with tolerance_rating masking)**
Per CONTEXT.md locked decision: "tolerance_rating blocked at BOTH RLS layer and serialization layer."

Implementation for `connect.connected_profiles`:
- ENABLE RLS.
- **Owner SELECT policy** (`connected_profiles_select_own`): `USING ((select auth.uid()) = user_id AND deleted_at IS NULL)` -- owner gets full row including `tolerance_rating`.
- **Non-owner authenticated SELECT policy** (`connected_profiles_select_others`): Create a **view** `connect.connected_profiles_public` that projects all columns EXCEPT `tolerance_rating`:
  ```sql
  CREATE VIEW connect.connected_profiles_public AS
    SELECT id, user_id, display_name, account_standing, verification_status,
           verification_method, verified_region, xp, gem_balance, gem_reserve_cap,
           veracity_rating, deleted_at, created_at, updated_at
    FROM connect.connected_profiles
    WHERE deleted_at IS NULL;
  ```
  Enable RLS on this view. Add authenticated SELECT policy: `USING (true)` -- any authenticated user can read the public view (which excludes tolerance_rating) for existence checks and cross-user reads.

  Alternatively (if the view approach is too complex for Supabase's RLS on views), use TWO SELECT policies directly on the table:
  - Owner policy: `USING ((select auth.uid()) = user_id AND deleted_at IS NULL)` -- returns full row
  - Non-owner policy: `USING (deleted_at IS NULL)` -- returns full row BUT combined with a security barrier view

  The executor should choose the approach that works cleanest with Supabase. The REQUIREMENT is: a SELECT by user B on user A's connected_profiles row must return NULL for tolerance_rating (masked at database layer). Only user A (where auth.uid() = user_id) receives the real tolerance_rating value. Test 2A/2B/2C in connect_profiles.sql will verify this.

- `connect.verification_sessions`: ENABLE RLS. Owner only (`(select auth.uid()) = user_id`).
- `connect.peer_connections`: ENABLE RLS. Participant read (requester_id OR addressee_id).
- `connect.account_follows`: ENABLE RLS. Follower reads own follows. Followed sees who follows them.
- `connect.gem_transactions`: ENABLE RLS. Owner read only.
