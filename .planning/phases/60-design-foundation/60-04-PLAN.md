  <name>Task 1: Create StepProgress component (DSGN-05)</name>
  <files>app/src/components/StepProgress.tsx</files>
  <action>
    Create a new file `app/src/components/StepProgress.tsx` containing a single named export `StepProgress`. The pattern is adapted from the XP progress bar in `app/src/pages/DashboardPage.tsx` (the existing `bg-gray-100 dark:bg-gray-800` track with a `bg-ev-teal` filled portion and `transition-all duration-700`), recolored to `bg-ev-blue` for v2.0.

    Implementation:

    ```typescript
    interface StepProgressProps {
      currentStep: number;
      totalSteps: number;
    }

    export function StepProgress({ currentStep, totalSteps }: StepProgressProps) {
      const safeTotal = Math.max(totalSteps, 1);
      const safeCurrent = Math.max(0, Math.min(currentStep, safeTotal));
      const percent = Math.round((safeCurrent / safeTotal) * 100);

      return (
        <div className="space-y-2">
          <div className="flex items-center justify-between text-sm text-gray-400">
            <span>Step {safeCurrent} of {safeTotal}</span>
            <span>{percent}%</span>
          </div>
          <div className="h-1.5 rounded-full bg-gray-800 overflow-hidden" aria-hidden="true">
            <div
              className="h-full rounded-full bg-ev-blue transition-all duration-500"
              style={{ width: `${percent}%` }}
            />
          </div>
        </div>
      );
    }
    ```

    Key constraints:
    - Defensive math: clamp `currentStep` to `[0, totalSteps]` so a consumer passing `currentStep={5}` with `totalSteps={3}` doesn't render a percent > 100. Clamp `totalSteps` to at least 1 to prevent division-by-zero.
    - `Math.round` the percent — fractional values look broken in the percentage label.
    - `bg-ev-blue` for the filled portion (NOT `bg-ev-teal`). Track is `bg-gray-800` (matches the AuthCard surface family).
    - `transition-all duration-500` — animates width changes when `currentStep` increases. Half-second is snappy without being jarring.
    - `aria-hidden="true"` on the bar — the screen-reader hint comes from the text label "Step X of Y", not the visual bar.
    - DO NOT include props for color, height, or label text. v2.0 design uses one shape; consumers don't need overrides. Keeping the API minimal prevents drift.
    - DO NOT use external animation libraries. Tailwind `transition-all` is the codebase pattern.

    WHY clamp inputs: in onboarding flows with tier-conditional steps, it's easy to pass a stale step number while a user transitions tiers. Defensive clamping prevents UI jank.

    WHY h-1.5 not h-2: the v2.0 design spec calls for a thinner bar than the existing DashboardPage XP bar (which is h-2). A 6px bar reads as "progress indicator" rather than "primary metric".

  <name>Task 2: Create AppNav component (DSGN-06)</name>
  <files>app/src/components/AppNav.tsx</files>
  <action>
    Create a new file `app/src/components/AppNav.tsx` containing a single named export `AppNav`. The pattern is adapted from `app/src/pages/DashboardPage.tsx` header (the existing white/dark-gray sticky header with brand text and a right slot), recolored to `bg-ev-navy` and using a logo image instead of pure text.

    Implementation:

    ```typescript
    import type { ReactNode } from 'react';

    interface AppNavProps {
      children?: ReactNode;
    }

    export function AppNav({ children }: AppNavProps) {
      return (
        <header className="bg-ev-navy border-b border-white/10 sticky top-0 z-10">
          <div className="max-w-lg mx-auto px-4 h-14 flex items-center justify-between">
            <div className="flex items-center gap-3">
              <img
                src="/logo.png"
                alt="Empowered Vote"
                className="h-6 w-auto"
              />
              <span className="text-sm font-semibold text-white/70">
                Civic Platform
              </span>
            </div>
            {children && (
              <div className="flex items-center gap-3">
                {children}
              </div>
            )}
          </div>
        </header>
      );
    }
    ```

    Key constraints:
    - `<img src="/logo.png" />` — Vite serves `app/public/logo.png` from the web root (path `/logo.png`). This requires plan 60-01 to have copied the asset. If the asset is missing, the image renders broken. See research pitfall #4.
    - DO NOT use `<Link>` or `<a>` around the logo. AppNav is a chrome component; navigation logic belongs to the consumer. Phase 64 (InformLanding) and Phase 65 (Dashboard) will wrap AppNav or not, as needed.
    - `max-w-lg` on the inner container — matches DashboardPage header width. The consumer page can override by wrapping AppNav in a wider container if needed (rare).
    - `h-14` sets the navbar height to 56px. `h-6 w-auto` on the logo gives a 24px tall logo, leaving comfortable vertical padding.
    - `text-white/70` on the wordmark — slightly muted so the logo carries primary visual weight.
    - `border-b border-white/10` — subtle bottom border, NOT a hard `border-gray-800`. Matches the navy aesthetic.
    - `sticky top-0 z-10` — keeps the nav pinned during scroll. z-10 is the codebase convention (matches DashboardPage header).
    - The right-slot div renders ONLY when `children` is provided. This avoids producing an empty flex container that affects spacing.
    - DO use named export. DO use `interface` for props.

    WHY no logo `<Link>` to '/': linking would couple AppNav to react-router and to a routing decision that varies by consumer (InformLanding might want logo→reload-self, Dashboard might want logo→/).

    WHY children prop and not separate `rightSlot` prop: idiomatic React composition. The consumer renders `<AppNav><SignInLink /></AppNav>` and the slot is obvious.
  </action>
