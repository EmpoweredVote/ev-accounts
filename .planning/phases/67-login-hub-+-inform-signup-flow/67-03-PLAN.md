<objective>
Add a `pool.query()` UPDATE in the existing POST /api/auth/signup handler so that when a user signs up via the Inform path (no invite_code), their `display_name` is persisted to `public.users`. The Zod schema already accepts `display_name`; the bug today is that this value is never written when invite_code is absent — the `on_auth_user_created` trigger creates `public.users(id)` with `display_name = NULL`, and the existing `signup_with_invite` RPC only runs when an invite_code is provided.

Purpose: Phase 67's success criterion 4 ("session reflects an Inform-tier account") implicitly requires that the Phase 68 yellow profile page can render the user's chosen display name. Without this fix, every Inform user has `display_name = NULL` and shows up as a nameless ghost on their own profile.

Output: One additive code block in `backend/src/routes/auth.ts` plus an automated test or curl-based verification that confirms display_name lands on public.users.
</objective>

Insert this block:

```ts
// Phase 67: Inform signup path persists display_name onto public.users.
// The on_auth_user_created trigger inserts public.users(id) with display_name = NULL.
// The Connected path (below) writes display_name through signup_with_invite RPC, so
// we ONLY do this UPDATE when no invite_code is present (Inform path).
// Non-fatal: if the UPDATE fails, the user is already created — they can update
// display_name from the profile page later. We log and continue.
if (!invite_code) {
  try {
    await pool.query(
      `UPDATE public.users
         SET display_name = $2,
             updated_at = now()
       WHERE id = $1`,
      [data.user.id, display_name]
    );
  } catch (updateErr) {
    console.error('[auth/signup] Failed to persist display_name for Inform user:', data.user.id, updateErr);
    // Intentionally non-fatal — proceed to 201 below.
  }
}
```

- DO NOT change the Zod schema (it already accepts `display_name` as required min 1 max 100).
- DO NOT modify the `if (invite_code && !legal_name)` 422 branch — it remains immediately after this new block.
- DO NOT touch the `signup_with_invite` RPC path — that already passes `p_display_name: display_name` and writes display_name itself (verified in research).
- DO NOT add a new endpoint, new RPC, or any schema migration. The `public.users.display_name` column already exists (nullable text) and is the right destination.
- The UPDATE uses `pool.query()` — public schema CAN go through PostgREST, but `pool.query()` is fine here and matches the project's pattern of using direct Postgres for writes (see [project memory: pool.query for non-public schemas]).
