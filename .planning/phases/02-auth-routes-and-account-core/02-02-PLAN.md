    **1. Create `backend/src/middleware/requireVerified.ts`:**

    This middleware checks that the authenticated user has confirmed their email. It runs AFTER `requireAuth` (which sets `req.userId` and `req.accessToken`). It uses `supabaseAdmin` for a trusted server-side check — this is permitted because it lives in `src/middleware/`, not `src/routes/`. The architecture test allowlist was updated in Plan 02-01 to include this file.

    ```typescript
    import { Response, NextFunction } from 'express';
    import type { AuthenticatedRequest } from './auth.js';
    import { supabaseAdmin } from '../lib/supabase.js';

    /**
     * Blocks unverified-email users from write endpoints.
     * Must be used AFTER requireAuth middleware.
     *
     * Uses supabaseAdmin.auth.admin.getUserById — a trusted server-side check,
     * not a data read for the response body. Same pattern as middleware/auth.ts.
     */
    export async function requireVerified(
      req: AuthenticatedRequest,
      res: Response,
      next: NextFunction
    ): Promise<void> {
      try {
        const { data: { user }, error } = await supabaseAdmin.auth.admin.getUserById(req.userId);

        if (error || !user?.email_confirmed_at) {
          res.status(403).json({
            code: 'EMAIL_NOT_VERIFIED',
            message: 'Email verification required for this action',
          });
          return;
        }

        next();
      } catch {
        res.status(500).json({
          code: 'INTERNAL_ERROR',
          message: 'An unexpected error occurred',
        });
      }
    }
    ```

    **PATCH /api/account/me:**

    Middleware chain: `requireAuth`, `requireVerified`, `requireConnected`

    Why this order:
    - `requireAuth`: Validates JWT, sets req.userId and req.accessToken
    - `requireVerified`: Blocks unverified-email users (read-only access decision from CONTEXT.md)

    Implementation:
    1. Validate body with Zod:
       ```typescript
       const PatchMeSchema = z.object({
         display_name: z.string().min(1).max(100).optional(),
         avatar_url: z.string().url().max(500).optional(),
       }).strict();
       ```
       Wait — the decision was to strip silently, not reject unknown fields. Use `.strip()` or just the default `.object()` behavior (which strips unknown keys by default in Zod). Do NOT use `.strict()`. Use:
       ```typescript
       const PatchMeSchema = z.object({
         display_name: z.string().min(1).max(100).optional(),
         avatar_url: z.string().url().max(500).optional(),
       });
       ```
       Zod `.object()` strips unknown keys by default. This silently ignores non-editable fields like tolerance_rating if sent.

    2. On Zod validation failure: return 422 `{ code: 'VALIDATION_ERROR', message: '<first issue>' }`
    3. Check that at least one field is being updated: if `Object.keys(result.data).length === 0` or all values are undefined, return 422 `{ code: 'VALIDATION_ERROR', message: 'No valid fields to update' }`
    4. Create user-scoped client: `const db = createUserClient(req.accessToken);`
    5. Update public.users (display_name and/or avatar_url):
       ```typescript
       const updateFields: Record<string, unknown> = {};
       if (result.data.display_name !== undefined) {
         updateFields.display_name = result.data.display_name;
       }
       if (result.data.avatar_url !== undefined) {
         updateFields.avatar_url = result.data.avatar_url;
       }

       if (Object.keys(updateFields).length > 0) {
         updateFields.updated_at = new Date().toISOString();
         const { error: updateError } = await db
           .from('users')
           .update(updateFields)
           .eq('id', req.userId);

         if (updateError) {
           // Log the error for debugging
           console.error('[PATCH /api/account/me] users update failed:', updateError);
           res.status(500).json({ code: 'INTERNAL_ERROR', message: 'Failed to update profile' });
           return;
         }
       }
       ```
