<objective>
Build and run a standalone tsx ingestion script that populates `essentials.politicians.finance_summary` for every federal politician using the FEC API. Closes FINA-02.

Purpose: Phase 90's value lives in the data, not the column. Without populated rows, FINA-03's API surface returns nothing useful. This plan ships the one-time ingestion that bridges the FEC API to the new JSONB column.

The script is one-shot (not a cron); it follows the project's established `run-fec-auto-match.ts` runner pattern. It walks federal politicians one at a time with a 1.5s inter-call sleep (well under FEC's 1,000 req/hr limit), makes three FEC calls per politician (search -> totals -> by_employer), builds a strict `{ total_raised, top_donors, cycle, source: "FEC" }` object, and writes it to the new JSONB column via `pool.query`. Non-matched politicians are skipped with a logged warning, not errored.

Output:
- `backend/scripts/run-fec-finance-summary.ts` — standalone tsx script
- Run summary log captured in SUMMARY.md (processed, succeeded, skipped, errors)
- finance_summary populated for the federal politician set (verified via SELECT COUNT)
</objective>

  <behavior>
    - When invoked with valid `FEC_API_KEY` and `DATABASE_URL`, script enumerates federal politicians by joining `essentials.politicians` -> `essentials.offices` -> `essentials.districts` filtered to `district_type IN ('NATIONAL_UPPER', 'NATIONAL_LOWER')` AND `is_active = true`
    - For each politician, the script resolves an FEC candidate_id using two-path lookup: Path 2 first (`transparent_motivations.politician_sources WHERE source_system LIKE 'fec%' AND research_status = 'confirmed' AND essentials_politician_id = $1`), Path 1 fallback (bioguide_id -> congress-legislators JSON -> `id.fec[]` filtered by current chamber: S-prefix IDs for senators, H-prefix for House)
    - For politicians where neither path yields an FEC ID, the script LOGS a warning, increments the `skipped` counter, and leaves `finance_summary` untouched (NULL). It does NOT error or abort.
    - For each matched politician, three sequential FEC API calls: (1) `/v1/candidates/search/?candidate_id=X` to get principal_committees[0].committee_id; (2) `/v1/candidates/totals/?candidate_id=X&cycle=2026` to get `results[0].receipts`; (3) `/v1/schedules/schedule_a/by_employer/?committee_id=Y&cycle=2026&per_page=15&sort=-total` to get the top employers
    - Between every FEC API call (across all politicians and all three call types) the script sleeps `SLEEP_BETWEEN_SEARCHES_MS` (1500ms) — this is the established project rate-limit posture
    - `top_donors` is filtered to entries where `employer != null && employer.trim() !== ''`, then truncated to the top 10 by `total` descending. Note: per RESEARCH.md open question #1, "NOT EMPLOYED" / "SELF EMPLOYED" entries are kept (they reflect grass-roots small-donor base)
    - `total_raised` is `Number(receipts)` from the totals response — never the raw string; never `JSON.stringify(rawFecResponse)`
    - `cycle` is the literal string `"2026"` for all politicians (per RESEARCH.md open question #2 — consistent across the 143-politician set)
    - `source` is the literal string `"FEC"`
    - The DB write is a parameterized `pool.query('UPDATE essentials.politicians SET finance_summary = $1::jsonb WHERE id = $2', [JSON.stringify(summaryObject), politicianId])`
    - Per-politician errors (FEC HTTP non-2xx, FEC response parse fail, DB UPDATE fail) are caught, logged, counted in `errors`, and the loop continues — one bad politician never aborts the batch
    - Final summary log to stdout includes `{ processed, succeeded, skipped_no_fec_id, errors, durationSec }` as a single JSON.stringify line for grep
  </behavior>
