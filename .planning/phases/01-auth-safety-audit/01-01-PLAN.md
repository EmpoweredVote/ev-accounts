**Test helper — createTestUser:**
Create a unique user per test:
```go
func createTestUser(t *testing.T) (username, password string) {
    username = fmt.Sprintf("testuser_%s", uuid.New().String()[:8])
    password = "TestPass123!"
    hashed, _ := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    user := User{
        UserID:         uuid.New().String(),
        Username:       username,
        HashedPassword: string(hashed),
    }
    db.DB.Create(&user)
    t.Cleanup(func() {
        db.DB.Where("user_id = ?", user.UserID).Delete(&Session{})
        db.DB.Where("user_id = ?", user.UserID).Delete(&User{})
    })
    return username, password
}
```

**Test cases:**

1. `TestLoginReturnsSessionCookie` — Create test user. POST /auth/login with `{"username": X, "password": Y}`. Assert response status is 200. Assert response has `Set-Cookie` header containing `session_id`. Assert response body contains `user_id` and `username`.

2. `TestSessionPersistsAcrossRequests` — Create test user. Login using `http.Client` with `cookiejar.New(nil)`. GET /auth/me using the same client (cookie jar carries session_id automatically). Assert /auth/me returns 200 with the correct username and user_id.

3. `TestLogoutClearsSession` — Create test user. Login with cookie jar client. POST /auth/logout using same client. GET /auth/me using same client. Assert /auth/me returns 401 after logout.

4. `TestTabReloadPreservesLogin` — Create test user. Login with cookie jar client. GET /auth/me (first request). GET /auth/me (second request, same client — simulates tab reload). Assert both requests return 200 with same user data. (This confirms cookie jar holds the session across multiple requests.)

5. `TestExpiredSessionRejected` — Create test user. Login with cookie jar client. Directly update the session in the database to set `expires_at` to 1 hour in the past:
```go
db.DB.Model(&Session{}).Where("user_id = ?", userID).Update("expires_at", time.Now().Add(-1*time.Hour))
```
GET /auth/me. Assert 401 response with body containing "Session expired".

**Important implementation notes:**
- Use `http.Client{Jar: jar}` for cookie round-tripping. Do NOT manually extract and set cookies.
- The login request body must be JSON: `{"username": "...", "password": "..."}`. The `User` model has a `password` JSON field (not `Password`).
- Each test must create its own user and clean up — no shared state between tests.
- Use `t.Helper()` in helper functions for better error reporting.

Create the directory `EV-Backend/docs/` and write `auth-audit.md` containing the complete auth audit. This is the primary deliverable document for Phase 1.

**Structure the document with these sections:**

**1. Overview**
Brief description: EV-Backend uses a hand-rolled, database-backed session system. Sessions stored in `app_auth.sessions`, validated per-request by `SessionMiddleware`, expired with a fixed 6-hour TTL (no sliding window).

**2. Cookie Configuration**

Two subsections — Production and Local Dev — showing every cookie attribute:

Production:
- Name: `session_id`
- Value: UUID v4
- Path: `/`
- MaxAge: 21600 (6 hours)
- HttpOnly: true
- Secure: true
- SameSite: None (required for cross-site Netlify+Render)
- Domain: (not set — intentionally omitted)

Local Dev:
- Same except: Secure=false, SameSite=Lax

Include the environment detection logic: `PORT` env var — if empty or starts with "5050", local dev mode. Note this as fragile (should be `APP_ENV` flag instead) but not a Phase 1 fix.

Source: `sessionCookie()` in `internal/auth/handlers.go` lines 20-40.

**3. Session Lifecycle**
Document the full flow: login creates/upserts session (6hr TTL), middleware validates on each request, logout deletes session record AND clears cookie (MaxAge=-1). Note: no sliding window — session expires exactly 6 hours after creation regardless of activity. Note: one session per user (upsert pattern in LoginHandler).

**4. Route Auth Level Manifest**

Start with a **summary table** grouped by auth level:

| Auth Level | Count | Description |
|------------|-------|-------------|
| public | 21 | No authentication required |
| auth-required | 27 | Valid session cookie required (SessionMiddleware) |
| auth-required + admin | 14 | Valid session + admin role required (SessionMiddleware + AdminMiddleware) |

Then provide the **detailed manifest grouped by module** — list every route for each module (auth, compass, essentials, treasury, staging, webhooks, root). Each entry: Method, Path, Auth Level, Handler name. Use the complete route data from the research file (01-RESEARCH.md "Complete Route Manifest" section).

**5. CORS Configuration**
Document the allowed origins list from `internal/middleware/middleware.go` (all 22 entries). Note that new deployment domains must be added to this map. Note that `Access-Control-Allow-Credentials: true` is set for all allowed origins, which is required for cross-origin cookie sends.

**6. Security Observations**
Document these as observations, not fixes:
- `UpdatePasswordHandler` duplicates session validation instead of using context userID (belt-and-suspenders, not a bug)
- `AdminCheckHandler` does its own role check despite being behind SessionMiddleware (correct but could be simplified)
- Port-based environment detection for cookie settings is fragile
- No CSRF protection (acceptable for API-only backend with SameSite cookies, but worth noting)
- Fixed 6-hour session TTL with no sliding window (security tradeoff: simpler but forces re-login every 6 hours)

**7. Domain Migration Notes**
When hosting consolidates under `*.empowered.vote`:
- Set cookie `Domain` to `.empowered.vote` (allows sharing across subdomains)
- Can downgrade `SameSite` from `None` to `Lax` (more secure, since all frontends will be same-site)
- Keep `Secure: true` always
- Update CORS origins list for new domains
- Frontend `VITE_API_URL` env vars may need updating
- Keep notes hosting-agnostic — don't assume Netlify/Render specifically

Source: `sessionCookie()` calls in `LoginHandler` (line 135) and `LogoutHandler` (line 185).

**8. Phase 2 Handoff**
Explicitly list what Phase 2 (Guest-First Auth) can assume is true after Phase 1:
1. Auth flow is verified — login, session persistence, logout, tab reload all have passing automated tests
2. Cookie config is documented — exact production settings are written down; no guessing
3. Route manifest exists — every route categorized as public, auth-required, or auth-required+admin
4. No guest-ok tier exists today — Phase 2 introduces it from scratch; no existing code to conflict with
5. SessionMiddleware is mockable — the SessionFetcher interface enables clean test doubles
6. CORS origin list is documented — new origins can be added knowing exactly where the list lives

**Routes Phase 2 will likely change from auth-required to guest-ok:**

- `POST /compass/answers/batch`
- `GET /compass/selected-topics` and `PUT /compass/selected-topics`

Do NOT use emojis. Use plain markdown. Keep the document factual and reference source file locations.
