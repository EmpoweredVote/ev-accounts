Create `backend/scripts/applyMigrations.ts`. This is a standalone Node.js script (not an Express route) that:

1. Loads `.env` via dotenv. Reads `DATABASE_URL` from environment. If not set, prints an error and exits 1.

2. Creates a `pg.Pool` using `DATABASE_URL`. The URL must be the direct connection (port 5432, `db.<ref>.supabase.co`), NOT the pooler (port 6543, `pooler.supabase.com`). Add a comment warning about this at the top of the file.

3. Defines a `MIGRATIONS` array in strict apply order:
   ```
   [
     { file: '026_inform_schema_repair_and_candidates.sql', label: '026' },
     { file: '027_rpc_reset_compass_answers.sql',          label: '027' },
     { file: '028_rpc_import_compass_calibrations.sql',    label: '028' },
     { file: '029_compass_admin_rpcs.sql',                 label: '029' },
   ]
   ```

4. Defines `PRE_VERIFY_QUERIES` and `POST_VERIFY_QUERIES` maps (keyed by label) for each migration:

   PRE (run before apply — asserts migration is NOT yet applied):
   - 026: `SELECT column_name FROM information_schema.columns WHERE table_schema='inform' AND table_name='politicians' AND column_name='is_candidate'` — expects 0 rows (no row means not applied yet). Skip pre-check and log "already applied" if 1 row exists, then skip applying this migration.
   - 027: `SELECT proname FROM pg_proc WHERE proname='reset_compass_answers'` — 0 rows means not applied.
   - 028: `SELECT proname FROM pg_proc WHERE proname='import_compass_calibrations'` — 0 rows means not applied.
   - 029: `SELECT proname FROM pg_proc WHERE proname='admin_create_topic_with_stances'` — 0 rows means not applied.

   POST (run after apply — asserts migration succeeded):
   - 026: same as 026 PRE but expect exactly 1 row.
   - 027: same as 027 PRE but expect 1 row.
   - 028: same as 028 PRE but expect 1 row.
   - 029: same as 029 PRE but expect 1 row.

5. For each migration in order:
   a. Run pre-verify. If result indicates already applied: log `[026] SKIP — already applied` and continue to next.
   b. Log `[026] Applying...`
   c. Read file from `backend/migrations/<file>` using `path.resolve(process.cwd(), 'backend/migrations', file)` (safe for tsx execution from repo root).
   d. Execute the SQL via `pool.query(sql)`.
   e. Run post-verify. If fails: log `[026] FAIL — post-verification failed` and exit 1.
   f. Log `[026] OK`.

6. On success: log `All migrations applied successfully.` and exit 0.

7. On any unexpected error: log the error and exit 1.

8. Use `async/await` throughout. Call `pool.end()` in a `finally` block.

Script is run with: `npx tsx backend/scripts/applyMigrations.ts`

TypeScript: strict mode, no `any`, import types from `pg`.

# Empowered Accounts — Deployment Runbook

## Overview

Brief: what this runbook covers (applying backend migrations to production Supabase, verifying the deployment, environment setup for Render + admin UI).

## Prerequisites

- Access to Supabase Dashboard for the production project
- Render dashboard access (backend service + admin UI static site)
- Direct Postgres connection string (port 5432, `db.<ref>.supabase.co`) — NOT the pooler URL (port 6543, `pooler.supabase.com`)
- All environment variables listed below

## Environment Variables

### Backend (Render service)

Table with columns: Variable | Source | Notes. Include all variables:
NODE_ENV, PORT, SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, DATABASE_URL, REDIS_URL, CORS_ORIGIN, QUEST_SERVICE_KEY, TRIVIA_SERVICE_KEY, ADMIN_SERVICE_KEY.

For DATABASE_URL, the Notes column must state:

> Direct connection only. Format: `postgresql://postgres.<ref>:<pwd>@db.<ref>.supabase.co:5432/postgres`
> Do NOT use the pooler URL (`pooler.supabase.com`, port 6543). Multi-statement migrations fail on the pooler.

### Admin UI (Vite static build)

VITE_API_URL — must be set at build time, not runtime. Explain why (Vite inlines env vars at build, not served).

## Step 1: Enable PostgreSQL Extensions

One-time setup in Supabase Dashboard → SQL Editor:

```sql
CREATE EXTENSION IF NOT EXISTS postgis WITH SCHEMA extensions;
CREATE EXTENSION IF NOT EXISTS pgcrypto WITH SCHEMA extensions;
```

Note: PostGIS is required for Phase 19 (location infrastructure). pgcrypto is required for Phase 19 (encrypted coordinates). Enable both now to avoid a second deploy window.

## Step 2: Apply Migrations

### Important: Use direct connection only

DATABASE_URL must use the direct connection format:

```
postgresql://postgres.<ref>:<pwd>@db.<ref>.supabase.co:5432/postgres
```

Port 5432, `db.<ref>.supabase.co` subdomain. NOT the pooler (`pooler.supabase.com`, port 6543). Multi-statement migrations fail on the pooler.

### Apply order (strictly sequential)

```
026 → 027 → 028 → 029
```

### Using the apply script (recommended)

```bash
DATABASE_URL="postgresql://postgres.<ref>:<pwd>@db.<ref>.supabase.co:5432/postgres" \
  npx tsx backend/scripts/applyMigrations.ts
```

The script: checks if each migration is already applied (idempotent), applies in order, runs post-verification queries, exits 1 on failure.

### Manual apply (fallback)

```bash
psql "$DATABASE_URL" -f backend/migrations/026_inform_schema_repair_and_candidates.sql
psql "$DATABASE_URL" -f backend/migrations/027_rpc_reset_compass_answers.sql
psql "$DATABASE_URL" -f backend/migrations/028_rpc_import_compass_calibrations.sql
psql "$DATABASE_URL" -f backend/migrations/029_compass_admin_rpcs.sql
```

### Post-apply verification queries

Run in Supabase Dashboard → SQL Editor to confirm each migration applied:

```sql
-- 026: is_candidate column on inform.politicians
SELECT column_name FROM information_schema.columns
WHERE table_schema = 'inform' AND table_name = 'politicians'
  AND column_name = 'is_candidate';
-- Expected: 1 row

-- 026: deleted_at column on inform.compass_responses
SELECT column_name FROM information_schema.columns
WHERE table_schema = 'inform' AND table_name = 'compass_responses'
  AND column_name = 'deleted_at';
-- Expected: 1 row

-- 027: reset_compass_answers RPC exists
SELECT proname FROM pg_proc WHERE proname = 'reset_compass_answers';
-- Expected: 1 row

-- 028: import_compass_calibrations RPC exists
SELECT proname FROM pg_proc WHERE proname = 'import_compass_calibrations';
-- Expected: 1 row

-- 029: admin_create_topic_with_stances RPC exists
SELECT proname FROM pg_proc WHERE proname = 'admin_create_topic_with_stances';
-- Expected: 1 row
```

## Step 6: Post-Deployment Housekeeping

Regenerate TypeScript types after migrations are applied, so local development reflects the updated schema:

```bash
supabase gen types typescript --project-id <ref> --schema public,connect,empower,inform \
  > backend/src/types/database.types.ts
```

Commit the regenerated file. Omitting this step leaves the local type definitions out of sync with production schema.

## Rollback

### Migration rollback SQL

If a migration must be reversed:

**026 rollback:**
```sql
ALTER TABLE inform.politicians DROP COLUMN IF EXISTS is_candidate;
ALTER TABLE inform.compass_responses DROP COLUMN IF EXISTS deleted_at;
DROP INDEX IF EXISTS inform.idx_compass_responses_user_active;
```

**027 rollback:**
```sql
DROP FUNCTION IF EXISTS public.reset_compass_answers(UUID, BOOLEAN);
```

**028 rollback:**
```sql
DROP FUNCTION IF EXISTS public.import_compass_calibrations(UUID, JSONB, BOOLEAN);
```

**029 rollback:**
```sql
DROP FUNCTION IF EXISTS public.admin_create_topic_with_stances(TEXT, TEXT, TEXT[], INT[], BOOLEAN);
DROP FUNCTION IF EXISTS public.admin_assign_topic_categories(INT, INT[]);
DROP FUNCTION IF EXISTS public.admin_list_politicians(BOOLEAN, INT, INT);
```

Note: 026 ADD COLUMN rollback is destructive — only run if no data has been written to these columns in production.

## Common Pitfalls

1. Do NOT apply files from `supabase/migrations/` — only `backend/migrations/026–029`.
2. Apply strictly in order: 026 → 027 → 028 → 029. Migration 029 references `inform.politicians.is_candidate` added in 026.
3. Use direct connection (port 5432, `db.<ref>.supabase.co`) for migration execution. Pooler (port 6543, `pooler.supabase.com`) does not support multi-statement transactions.
4. `VITE_API_URL` must be set at build time. Changing it after the build requires a rebuild.
5. `backend/scripts/applyMigration.js` does NOT exist — use `applyMigrations.ts` (this file) or `psql -f`.
