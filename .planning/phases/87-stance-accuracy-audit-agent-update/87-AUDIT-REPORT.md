## Methodology

This audit uses two complementary approaches to identify politicians whose stance data may contain research errors:

**Source 1 — Pre-seeded confirmed inversions (Tier 1).** An informal audit conducted on 2026-06-02 identified 8 politicians with confirmed stance inversions — cases where the documented stances systematically reflect the wrong ideological direction. These 8 entries are placed directly into the `confirmed-inversion` tier regardless of what the SQL query returns. They require full re-research in Phase 88.

**Source 2 — SQL low-variance flag (Tiers 2 and 3).** A PostgreSQL query identifies politicians where a single value accounts for at least 60% of their total stances, restricted to politicians with 15 or more stances. The 60% threshold applied to a minimum of 15 stances returns 247 rows (per RESEARCH.md Pattern 2 verified counts). This threshold was kept as recommended because: (a) 247 falls within the planner's "signal-rich but workable" discretion window after the confirmed-inversion tier is separated; (b) lowering further would pull in politicians with only 3–6 stances who trivially hit 60%; (c) raising to 70% would miss researchers with 62–69% dominance patterns that are still suspicious.

**Why party distribution is NOT the primary flag signal.** The Empowered Vote compass uses a five-chairs framing: each topic has five distinct, substantive positions a real person can hold. The spoke has no correct end — value=1 is not "conservative" and value=5 is not "progressive" — direction varies by topic. Using party-distribution comparison as the primary audit metric would encode directional partisan assumptions that the five-chairs philosophy explicitly rejects. Party direction is only used in this report to assign already-flagged SQL rows to a tier (borderline vs. likely-correct) — it does not determine whether a politician is flagged.

**Three priority tiers.** The report organizes flagged politicians into three tiers:
- `confirmed-inversion` — 8 pre-seeded entries from the 2026-06-02 informal audit. These are confirmed errors requiring full re-research.
- `borderline` — SQL-flagged rows that show a cross-party suspicious pattern (Republican dominant ≤ 2, Democrat/Democratic dominant ≥ 4), a uniform-neutral lock (dominant value = 3 at ≥ 80% ratio), or any value lock ≥ 90% regardless of party. These have higher probability of being research errors.
- `likely-correct` — SQL-flagged rows that follow expected partisan distributions (Democrat/Democratic dominant value = 1 or 2; Republican dominant value = 4 or 5) or are Unknown party. These follow natural ideological alignment and are lowest priority for re-research.

**Jeff Gonzalez multi-value inversion.** The single-dominant-value SQL cannot catch Jeff Gonzalez's pattern. His stances are split across values 1 (43%) and 2 (38%) — both on the wrong side for a Republican, but neither crosses 60% individually. He is correctly pre-seeded as a confirmed inversion and would not appear in the SQL-derived tiers. This is documented in RESEARCH.md Pattern 3.

**Adam Hinojosa.** With only 6 stances, Hinojosa is below any reasonable SQL minimum-stance filter and is pre-seeded manually. His 6 stances appear to reflect Republican-leaning positions despite his `party` tag of "Democrat" — the tag itself may be wrong (Phase 88 should verify).

## Audit SQL

The following SQL can be re-run in future milestones to reproduce this audit. Run from the `backend/` directory: load environment variables (`set -a && source .env && set +a`), then invoke via `node --import tsx` importing `pool` from `./src/lib/db.js`. All `inform.*` access must use `pool.query()` — the `inform` schema is not in Supabase's PostgREST exposed schemas list.

```sql
-- Audit SQL: 60% dominant-value flag with per-politician breakdown
-- Run via: pool.query(SQL) in backend/src/lib/db.js context
-- Minimum stance count (currently 15) is the planner's discretion tuning knob
-- See RESEARCH.md Pattern 2 for threshold count table (60%+15 = 247, 60%+20 = 164, 70%+15 = 127)

WITH per_politician_totals AS (
  SELECT politician_id, COUNT(*) AS total_stances
  FROM inform.politician_answers
  GROUP BY politician_id
),
per_value_counts AS (
  SELECT politician_id, value, COUNT(*) AS cnt
  FROM inform.politician_answers
  WHERE value = ROUND(value)   -- exclude half-values (63 rows: 1.5, 2.5, 3.5, 4.5)
  GROUP BY politician_id, value
),
per_politician_max AS (
  SELECT pvc.politician_id, MAX(pvc.cnt) AS max_cnt
  FROM per_value_counts pvc
  GROUP BY pvc.politician_id
),
flagged_politicians AS (
  SELECT
    pvc.politician_id,
    pvc.value AS dominant_value,
    pvc.cnt AS dominant_count,
    ppt.total_stances,
    ROUND(pvc.cnt::numeric / ppt.total_stances * 100) AS ratio_pct
  FROM per_value_counts pvc
  JOIN per_politician_totals ppt ON ppt.politician_id = pvc.politician_id
  JOIN per_politician_max ppm
    ON ppm.politician_id = pvc.politician_id AND ppm.max_cnt = pvc.cnt
  WHERE pvc.cnt::numeric / ppt.total_stances >= 0.60
    AND ppt.total_stances >= 15        -- <-- tuning knob; lower to catch all 8 confirmed inversions
)
SELECT
  p.full_name                      AS name,
  COALESCE(NULLIF(p.party, ''), 'Unknown') AS party,
  (SELECT o.title FROM essentials.offices o
   WHERE o.politician_id = p.id LIMIT 1) AS office,
  fp.total_stances                 AS stance_count,
  fp.dominant_count                AS flagged_count,
  fp.ratio_pct                     AS flag_ratio_pct,
  fp.dominant_value,
  (
    SELECT string_agg(t.topic_key, ', ' ORDER BY t.topic_key)
    FROM inform.politician_answers pa
    JOIN inform.compass_topics t ON t.id = pa.topic_id
    WHERE pa.politician_id = fp.politician_id
      AND pa.value = fp.dominant_value
  )                                AS flagged_topics
FROM flagged_politicians fp
JOIN essentials.politicians p ON p.id = fp.politician_id
ORDER BY fp.ratio_pct DESC, fp.total_stances DESC;
```
