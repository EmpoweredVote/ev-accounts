**Create `backend/src/routes/connect.ts`:**

CRITICAL: This file MUST NOT contain the string "supabaseAdmin" anywhere — not in code, not in comments. The architecture test does a raw string check. All admin-level DB operations must go through service files in lib/ or use the pg pool directly.

Import `pool` from `../lib/db.js` for transactional writes (connected_profiles INSERT). Import `createUserClient` from `../lib/supabase.js` for RLS-enforced reads. Import `claimInviteCode` from `../lib/inviteService.js`. Import Zod for request validation.

**Step state machine:** `invite` -> `profile` -> `review` -> `complete`

Routes:

**1. POST /api/connect/start** — Begin or resume the Connect flow.
- Middleware: `requireAuth` only
- Body: `{ code: z.string().min(9).max(9) }` (the invite code)
- Logic:
  1. Check if user already has a connected_profiles record (query via pg pool: `SELECT id FROM connect.connected_profiles WHERE user_id = $1`). If yes, return 409 `{ code: 'ALREADY_CONNECTED', message: 'You already have a Connected profile' }`.
  2. Check if user already has a verification_session. If yes AND step_reached !== 'invite', return the existing session (resume flow — return 200 with current step and draft data).
  3. If no existing session OR session is at 'invite' step: call `claimInviteCode(code, userId)`. If claim fails, return the appropriate error (map from ClaimResult errors — same mapping as invites.ts claim route).
  4. On successful claim: UPSERT into `connect.verification_sessions` (INSERT ... ON CONFLICT (user_id) DO UPDATE) with `step_reached = 'profile'`, `invite_code_id = <the claimed code's id>`. To get the code's ID, the claimInviteCode function should be updated to also return the code ID — OR query it separately. SIMPLER: extend claimInviteCode return type to include `codeId` on success. If you cannot modify inviteService (it was created in Plan 02), query the code ID from invite_codes table via pg pool after successful claim.
  5. Return 200 `{ session_id, step_reached: 'profile', drafts: { display_name_draft, legal_name_draft, region_draft, home_address_draft } }`.

**2. PATCH /api/connect/step** — Update draft fields for the current step.
- Middleware: `requireAuth`
- Body validation via Zod:
  ```typescript
  z.object({
    step: z.enum(['profile', 'review']),
    display_name: z.string().min(1).max(100).optional(),
    legal_name: z.string().min(1).max(200).optional(),
    location: z.string().min(1).max(200).optional(),
    home_address: z.string().min(1).max(500).optional(),
  })
  ```
- Logic:
  1. Fetch user's verification_session via pg pool.
  2. If no session, return 404 `{ code: 'NO_SESSION', message: 'No active verification session' }`.
  3. If session step_reached is 'complete', return 409 `{ code: 'ALREADY_COMPLETE' }`.
  4. Update draft fields that were provided (only the ones sent in the body). Use pg pool UPDATE with named parameters.
  5. If `step` is 'review' and ALL required fields are present (display_name_draft, legal_name_draft, region_draft, home_address_draft all non-null), advance `step_reached` to 'review'.
  6. If `step` is 'profile', keep step_reached at 'profile' (user is still filling fields).
  7. Return 200 with updated session state.

**3. POST /api/connect/complete** — Finalize the Connect flow and create connected_profiles.
- Middleware: `requireAuth`
- Logic (ALL inside a pg pool transaction — BEGIN/COMMIT):
  1. SELECT verification_session WHERE user_id = $1 FOR UPDATE.
  2. Validate: session exists, step_reached = 'review', all 4 required draft fields are non-null.
  3. If any validation fails, ROLLBACK and return 400 with specific error.
  4. Check idempotency: SELECT FROM connected_profiles WHERE user_id = $1. If exists, ROLLBACK and return 409 `{ code: 'ALREADY_CONNECTED' }`.
  5. INSERT INTO connect.connected_profiles:
     - `user_id`: from auth
     - `display_name`: from session.display_name_draft
     - `legal_name`: from session.legal_name_draft
     - `home_address`: from session.home_address_draft
     - `account_standing`: 'active'
     - `verification_status`: 'verified'
     - `tolerance_rating`: 10.00 (explicit, matching DEFAULT)
     - `verified_region`: from session.region_draft
  6. UPDATE verification_session SET step_reached = 'complete'.
  7. Also UPDATE public.users SET display_name = session.display_name_draft WHERE id = user_id (sync display_name, same pattern as PATCH /api/account/me).
  8. COMMIT.
  9. Return 201 `{ connected: true, verification_status: 'verified', tier: 'connected' }`.

**4. GET /api/connect/status** — Check current verification status.
- Middleware: `requireAuth`
- Logic:
  1. Query connected_profiles for this user via pg pool (just `SELECT verification_status FROM connect.connected_profiles WHERE user_id = $1`).
  2. If no connected_profiles, check for verification_session and return `{ status: 'in_progress', step_reached: session.step_reached }` or `{ status: 'not_started' }`.
  3. If connected_profiles exists, return `{ status: data.verification_status }` (pending/verified/suspended).

**5. POST /api/connect/compass-import** — Import compass calibration from client.
- Middleware: `requireAuth`
- Body validation:
  ```typescript
  z.object({
    calibrations: z.array(z.object({
      topic_id: z.string().uuid(),
      topic_version: z.number().int().positive(),
      stance_id: z.string().uuid(),
      inverted: z.boolean().optional().default(false),
    })),
    confirmed: z.boolean().optional().default(false),
  })
  ```
- Logic (two-phase as described in RESEARCH.md Pattern 10):
  1. Fetch user's verification_session.
  2. If no session, return 404.
  3. If `confirmed: false` (first call — validation phase):
     - Query current live topics from `inform.compass_topics` via pg pool: `SELECT id, version FROM inform.compass_topics WHERE is_active = true`.
     - Compare each calibration's `topic_version` against the live version.
     - Return 200 with `{ valid: [...matching calibrations], mismatched: [...mismatched with { topic_id, client_version, server_version }], ready_to_import: mismatched.length === 0 }`.
  4. If `confirmed: true` (second call — save phase):
     - Store the calibrations JSON in verification_sessions.compass_import_draft as JSONB.
     - Return 200 `{ imported: true, count: calibrations.length }`.
     - NOTE: The actual write to inform.compass_responses happens in Phase 4. This plan stores the data in the session draft only.

Export as `connectRouter`.
