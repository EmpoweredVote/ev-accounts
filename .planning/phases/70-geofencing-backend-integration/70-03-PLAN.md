<objective>
Build the admin bulk re-cache mechanism for `connect.user_districts`. Used after redistricting events or new TIGER data imports to refresh the cache for users whose districts may have changed. Runs as a one-off command, not an HTTP endpoint — this is operator-facing infrastructure.

Purpose: Closes the redistricting-readiness gap from CONTEXT.md. Mid-decade redistricting is real (gerrymandering); when boundaries change, every affected user's `user_districts` rows are stale until re-resolved. Without this script the only way to refresh is to wait for each user to update their location individually.

Output: 1 SQL migration creating two stored procedures (the per-user and bulk variants), 1 TypeScript orchestrator script in `backend/scripts/`. No HTTP endpoints, no frontend changes, no env var additions.
</objective>

The migration creates TWO functions:

**Function A: `essentials.recache_user_districts_for_user(p_user_id uuid)` — per-user variant**

Decrypts the user's encrypted_lat/lng (using the same Vault key + pgp_sym_decrypt_bytea pattern as `connect.resolve_user_jurisdiction`), then calls `essentials.cache_user_districts(p_user_id, lat, lng)` to refresh their `user_districts` rows. Returns a small status JSONB (`{ user_id, layers_resolved: int, status: 'ok' | 'no_coords' | 'no_match' }`).

This is the single-user variant. It exists for two reasons: (a) tested and inspectable for one user before running bulk; (b) callable independently if an operator needs to refresh just one user post-incident.

Mandatory pattern (from RESEARCH.md + memory.md):
- `LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''`
- All references fully qualified (`extensions.pgp_sym_decrypt_bytea`, `vault.decrypted_secrets`, `connect.connected_profiles`, `essentials.cache_user_districts`, `connect.user_districts`)
- Vault key name: `location_encryption_key` (same key used by `connect.resolve_user_jurisdiction`)
- Decrypt pattern: `convert_from(extensions.pgp_sym_decrypt_bytea(v_encrypted_lat, v_key), 'UTF8')::float8`
- Read-side guard: only proceed if `connected_profiles.location_consent = true` AND `encrypted_lat IS NOT NULL` — otherwise return `status='no_coords'` without raising
- After calling `cache_user_districts`, count how many rows now exist for this user in `connect.user_districts` and report it via the JSONB return

**Function B: `essentials.recache_user_districts_bulk(p_cutoff timestamptz DEFAULT NULL)` — bulk variant**

Iterates Connected users matching the cutoff filter and calls `recache_user_districts_for_user` for each. Returns a SETOF rows (`user_id uuid, layers_resolved int, status text`) so the orchestrator script can stream and tally results.

Selection criteria:
- If `p_cutoff IS NULL`: process every user with `encrypted_lat IS NOT NULL AND location_consent = true` in `connect.connected_profiles`
- If `p_cutoff IS NOT NULL`: process every user where `(connect.user_districts.resolved_at < p_cutoff OR connect.user_districts.user_id IS NULL — i.e. has consented coords but no cache rows at all)` AND `connect.connected_profiles.encrypted_lat IS NOT NULL AND location_consent = true`

Implementation hint for cutoff variant — use a LEFT JOIN so users with no `user_districts` rows are included (their MIN(resolved_at) is NULL, which is treated as "older than cutoff"):

```sql
SELECT cp.user_id
  FROM connect.connected_profiles cp
  LEFT JOIN connect.user_districts ud ON ud.user_id = cp.user_id
 WHERE cp.encrypted_lat IS NOT NULL
   AND cp.location_consent = true
 GROUP BY cp.user_id
HAVING (p_cutoff IS NULL OR COALESCE(MIN(ud.resolved_at), '-infinity'::timestamptz) < p_cutoff)
```

Mandatory pattern:
- `LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''`
- All cross-schema references fully qualified
- For each candidate user_id, call `essentials.recache_user_districts_for_user(uid)` and `RETURN NEXT` a row built from its result
- Wrap each per-user call in `BEGIN ... EXCEPTION WHEN OTHERS THEN ... END;` so one bad user doesn't abort the whole bulk run; in the exception branch return `{ status: 'error', layers_resolved: 0 }`

**GRANTs:**

```sql
-- per-user variant: callable by service_role only (admin operations)
REVOKE ALL ON FUNCTION essentials.recache_user_districts_for_user(uuid) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION essentials.recache_user_districts_for_user(uuid) TO service_role;

-- bulk variant: same
REVOKE ALL ON FUNCTION essentials.recache_user_districts_bulk(timestamptz) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION essentials.recache_user_districts_bulk(timestamptz) TO service_role;
```

Do NOT grant to `authenticated` or `anon` — these are admin-only.

**File structure:** Wrap entire migration in `BEGIN; ... COMMIT;`. Add a comment header at the top describing what the migration does, the date, and which Phase/requirement (Phase 70 / GEO-10 follow-up infrastructure).

**No-op safety:** If the migration is run on an environment where `essentials.cache_user_districts` doesn't exist (i.e. Phase 69 wasn't applied), the migration should fail loudly during the `CREATE OR REPLACE FUNCTION` of `recache_user_districts_for_user`. That's correct — we don't need a defensive guard.
