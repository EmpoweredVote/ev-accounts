<task type="auto">
  <name>Task 2: Fix CalibrationOverlay race condition and resume-mode persistence</name>
  <files>CompassV2/src/components/CalibrationOverlay.jsx, CompassV2/src/pages/Compass.jsx</files>
  <action>
**CalibrationOverlay.jsx changes:**

1. **Remove the resume-mode persistence exclusion (line 271).** The line `if (resumeMode) return;` in the persist effect (line 268-274) prevents resume-mode sessions from saving progress. Remove this guard so that resume-mode progress IS saved to localStorage under the same `calibration_progress` key. This ensures refresh during resume-mode restores position.

2. **Fix the init effect (line 255-265) to always wait for topics.** Currently the guard `if ((resumeMode || startAtPick) && topics.length === 0) return;` only waits for topics when resumeMode or startAtPick. Change this to always wait: `if (topics.length === 0) return;`. This prevents the standard flow from initializing with stale data before topics load. Since Compass.jsx now gates on topicsLoaded, topics will always be non-empty when CalibrationOverlay mounts — but the defensive check is still good practice.

3. **Store resumeMode in calibration_progress.** In the persist effect, add `resumeMode` to the saved object:
   ```js
   const progress = { step, pickedTopics, currentIndex, resumeMode: resumeMode || false };
   ```

4. **In getInitialState(), read resumeMode from saved progress.** Before checking the `resumeMode` prop, check if saved calibration_progress has `resumeMode: true`. If so, restore the saved state (step, pickedTopics, currentIndex) instead of re-deriving from selectedTopics. This handles the refresh scenario where the component re-mounts and the `resumeMode` prop from Compass.jsx may be stale:
   ```js
   // Check localStorage for in-progress session (handles both standard and resume-mode)
   try {
     const saved = localStorage.getItem(STORAGE_KEY);
     if (saved) {
       const parsed = JSON.parse(saved);
       if (parsed.step === "pick" || parsed.step === "answer") {
         return {
           step: parsed.step,
           pickedTopics: parsed.pickedTopics || [],
           currentIndex: parsed.currentIndex || 0,
         };
       }
     }
   } catch {}
   ```
   Move this localStorage check to be the FIRST thing in `getInitialState()`, before the `startAtPick` and `resumeMode` prop checks. If there's valid saved state, always use it. The `startAtPick` and `resumeMode` branches remain as fallbacks for when there's no saved progress.

5. **Complete screen edge case (per user decision):** In the `getInitialState()` function, if all pickedTopics in saved progress are already answered (no unanswered topics), return `{ step: "welcome", pickedTopics: [], currentIndex: 0 }` — this effectively means calibration is done, and the CalibrationOverlay will show the fallback loading state briefly before Compass.jsx's `onComplete` fires. Actually, per user decision: "If all topics are answered and user refreshes on the complete celebration screen, skip celebration and go straight to compass." Handle this in Compass.jsx instead: when computing `needsCalibration`, if `calibration_progress` exists in localStorage but all topics are already answered, clear it and don't show calibration.

**Compass.jsx additional change:**

6. After the topicsLoaded gate and before `needsCalibration`, add a cleanup check: if `calibration_progress` exists in localStorage but every pickedTopic in it is already answered (meaning user was on the "complete" celebration screen when they refreshed), clear `calibration_progress` and set `calibrationActive` to false. This sends them straight to the compass per the user decision.

7. Also per user decision: "resume-mode flow must also survive refresh." The `resumeMode` computation in Compass.jsx (line 291) uses `answeredCompassCount > 0 && unansweredCompassTopics.length > 0`. When restoring from saved `calibration_progress` with `resumeMode: true`, the `calibrationActive` state (line 257-259) will be true from `!!localStorage.getItem("calibration_progress")`, which is correct — the overlay will show. The `resumeMode` prop passed to CalibrationOverlay may not match the saved value, but since we moved localStorage restoration to be first in `getInitialState()`, the saved state takes priority regardless of the prop value.
