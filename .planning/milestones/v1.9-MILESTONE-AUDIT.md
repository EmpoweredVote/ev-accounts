Scoped grants will correctly return only politicians with matching district records. Politicians lacking office records in the `essentials` schema will not appear for scoped editors.

## Tech Debt by Phase

### Phase 58 — Contributor Portal
- **ROLE-13 domain:** Portal is at `app.empowered.vote/contributor`, not `contributors.empowered.vote`. No separate Vite app. Alpha-acceptable given `app/` already exists and works; address before GA if a standalone contributor URL is needed.
- **CORS_ORIGIN:** Verify `app.empowered.vote` is in Render's `CORS_ORIGIN` env var. Not committed anywhere.
- **CTC guidance correction:** Update Phase 57 summary and any integration docs that claim `/api/contributor/me` exposes CTC grants. It does not. CTC uses `/api/roles/me` or `/api/roles/check`.
- **REQUIREMENTS.md stale checkboxes:** ROLE-01, 02, 13–16 show `[ ]`. Update to `[x]` to reflect completion.

### Location Infrastructure — resolve_user_jurisdiction / resolve_user_local_officials Disagreement
- **Bug (flagged 2026-04-10 by Essentials):** `resolve_user_jurisdiction` stores `city_council_geo_id = council_district:2` (San Fernando Valley) for a 90066 address (Mar Vista — should be District 11, Traci Park). `resolve_user_local_officials` returns District 11 correctly via live PostGIS. The two RPCs **must agree**. Root cause: either the geofence boundary dataset used by `resolve_user_jurisdiction` has a gap around 90066, or the two RPCs use different spatial data sources. Display is unaffected today (Path 1 of `representatives/me` uses the live query), but any logic that gates on the stored `city_council_geo_id` will silently use the wrong district. Needs investigation before any hard jurisdiction gate uses `city_council_geo_id`.

### Phase 55 — Compass Stance Editor
- **fail-open for missing geoid** (`stanceService.ts` line ~123): `getMatchingGrant` console.warns and returns null when politician has no `home_jurisdiction_geoid`. Intentional Alpha behavior. The Plan 58-05 live-join approach in `getEditorMatchingGrant` (Phase 56 pattern) is the correct long-term approach — backport to `getMatchingGrant` eventually.

### Phase 54 — Admin UI
- **Admin grant chain unverified:** `GrantRoleModal` → `adminRouter` route → `grantRole` RPC chain was not end-to-end traced by integration checker. Should be smoke-tested in production before v2.0.

### Phase 53 — Service Layer
- **Naming confusion in `/api/roles/check`:** Body field `feature_scope` accepts a role slug (e.g. `"volunteer"`), not a feature scope string. The name matches the grant column but semantically it's a slug. Works correctly but will confuse future integrators. Low priority rename or doc clarification.
