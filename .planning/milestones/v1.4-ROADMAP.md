## Phases

### Phase 27: Verification Rating Schema

**Goal**: Users have a Verification Rating that reflects their VQ accuracy, and the API exposes it with hold state and Red Gem unlock status.
**Depends on**: Phase 26 (v1.3 complete)
**Requirements**: VR-01, VR-02, VR-03, VR-04
**Plans**: 1 plan

Plans:

- [x] 27-01-PLAN.md — Migration 037 (verification_rating + vq_hold_until columns) and /me API response update with derived booleans

**Details:**

Migration 037 adds `verification_rating` (INTEGER NOT NULL DEFAULT 60, CHECK 0–150) and `vq_hold_until` (TIMESTAMPTZ nullable) to `connect.connected_profiles` with a partial index for hold-state queries. Updated `connected_profiles_public` view includes `verification_rating` but intentionally excludes `vq_hold_until` (same privacy pattern as `tolerance_rating`). Both GET and PATCH `/me` handlers updated to return `verification_rating`, `vq_hold_active`, and `red_gem_quests_unlocked` at root with safe inform-tier defaults.

Key patterns: Server-side derived booleans (clients never parse raw timestamps); privacy layering (vq_hold_until excluded from public view); default-forward (Inform-tier users get safe defaults at root).

### Phase 28: VQ Confirmation Flow

**Goal**: VQ can call a single authenticated endpoint to resolve a question — awarding Red Gems to correct answerers, adjusting Verification Ratings in both directions, writing the confirmed stance, and doing nothing on replay.
**Depends on**: Phase 27
**Requirements**: VQ-01, VQ-02, VQ-03, VQ-04, VQ-05, VQ-06
**Plans**: 2 plans

Plans:

- [x] 28-01-PLAN.md — Migration 038 (vq_confirmation_results table + confirm_vq_stance RPC) + route + service file + registration
- [x] 28-02-PLAN.md — Integration tests covering all 6 VQ requirements

**Details:**

Migration 038 delivers `connect.vq_confirmation_results` (idempotency result cache) and `connect.confirm_vq_stance` SECURITY DEFINER RPC. RPC: pre-check idempotency cache before any lock/write → acquire `pg_advisory_xact_lock` on all users (correct + incorrect combined, sorted UUID order) → correct users: inline gem INSERT + balance UPDATE + LEAST(vr+3, 150) → incorrect users: GREATEST(vr-10, 0) + CASE vq_hold_until when rating hits 0 → upsert `inform.politician_answers` with confirmed_value → cache result in `vq_confirmation_results`.

Key decisions: No nested SECURITY DEFINER calls (gem ledger inline); per-user idempotency sub-key (`p_idempotency_key || ':' || uid::text`); idempotency pre-check before lock acquisition; sorted UUID advisory locks for deadlock prevention.

Integration tests: 10 non-live tests + 12 live DB tests covering all VQ-01–VQ-08 requirements with `skipIf(!hasLiveDB)` / `skipIf(!hasVqFixtures)` guards.

## Milestone Summary

**Key Decisions:**

- verification_rating default 60 — baseline unverified; 90+ unlocks Red Gem quests
- vq_hold_until excluded from connected_profiles_public view — same privacy pattern as tolerance_rating
- No nested SECURITY DEFINER calls — gem INSERT + balance UPDATE done inline in confirm_vq_stance
- Advisory locks acquired on ALL users (correct + incorrect) in sorted UUID order before any writes — prevents deadlocks
- Per-user idempotency sub-key (main_key:uid) for gem_transactions — prevents double-crediting
- Idempotency pre-check before lock acquisition — cheapest replay path
- VQ service uses GEMS_SERVICE_KEYS / requireGemServiceKey (same auth model as gems endpoint)

**Issues Resolved:**

- PostGIS `extensions.ST_*` vs `public.ST_*` schema discrepancy found and fixed during Phase 30 live review
- Gem middleware reading wrong header (`Authorization: Bearer` vs `X-Service-Key`) — found and fixed during Phase 30 live review
- service_role missing SELECT grants on xp_transactions and gem_transactions — fixed during Phase 30 live review
- REQUIREMENTS.md had 9 stale Pending statuses from Phase 29/30 completion post-dating the last file update — reconciled before archive

**Issues Deferred:**

- CTC gem awards bypass accounts API (direct RPC call) — known pre-existing gap, tracked in MEMORY.md, not a v1.4 issue
- Profile Hub should eventually migrate to Framer production frontend — acceptable for Alpha (admin app dual-purpose)

**Technical Debt Incurred:**

- Admin React app serves dual purpose (/admin/* and /profile, /login, /signup) — separation of concerns concern for post-Alpha; acceptable at pilot scale
