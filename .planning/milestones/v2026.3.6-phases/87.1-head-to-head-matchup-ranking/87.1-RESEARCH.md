# Phase 87.1: Head-to-Head Matchup Ranking - Research

**Researched:** 2026-03-15
**Domain:** React animation patterns, pairwise comparison UX, Zustand store migration, Framer Motion
**Confidence:** HIGH

## Summary

This phase replaces drag-to-rank in EV-readrank with a pairwise head-to-head matchup flow. The reference concept (`concept-i-maximum.jsx`) is a complete, standalone working prototype of the full mechanic — the algorithm, state machine, animations, and layout are all already proven. The primary task is adapting that component's logic and animation patterns into the existing React/TypeScript/Framer Motion/Zustand codebase, replacing the two drag-rank components (AgreedQuotesSidebar / InlineRankPanel) with a MatchupPhase component and a wins-based RankedListSidebar.

The core algorithm is straightforward: track a `wins` counter per quote ID, iterate through all N*(N-1)/2 pending pairs after each swipe-agree, resume swipe mode when no pending pairs remain, compute final rankings by wins descending. The Zustand store needs modest additions (wins record, completedPairs set, mode field) without breaking the existing `rankedQuotes` single-source-of-truth.

**Primary recommendation:** Adopt the reference concept's state machine and animation keyframes directly. Adapt to Framer Motion (already installed) instead of raw CSS animations where possible, use EV color palette throughout, and keep the store version bump as the first commit to wipe stale localStorage.

### Pattern 1: Matchup State Machine

The concept uses `mode` as a local string (`"swipe" | "matchup" | "done"`). In the Zustand store this maps to a `matchupMode` field within `IssueProgress`.

**State additions to `IssueProgress`:**
```typescript
// Add to IssueProgress interface
matchupWins: Record<string, number>;       // quoteId -> win count
completedMatchupPairs: string[];           // sorted pairKeys: "id1-id2"
activeMatchupPair: [string, string] | null; // IDs of current pair
```

**Flow:**
1. `agreeWithQuote` fires → adds to `rankedQuotes` (unchanged)
2. If `rankedQuotes.length >= 2`, check `getPendingMatchups(rankedQuotes, completedMatchupPairs)`
3. If pending pairs exist, set `activeMatchupPair` → EvaluationPhase renders MatchupPhase instead of QuoteCard
4. User picks winner → `recordMatchupWin(winnerId, pairKey)` → store updates wins + completedPairs
5. Check pending pairs again; if none, clear `activeMatchupPair` → resume swipe mode OR go to results
6. `rankedQuotes` rank fields recalculated from wins on each store update

**Key insight from reference:** Matchup interrupts swipe mid-sequence, not just at the end. After each agree that creates new pairs, those pairs must be completed before the next swipe card appears.

### Pattern 2: Pair Generation Algorithm

```typescript
// Source: concept-i-maximum.jsx lines 11-18 (adapted)
export function getPendingMatchups(
  agreed: RankedQuote[],
  completedPairKeys: string[]
): [string, string][] {
  const completedSet = new Set(completedPairKeys);
  const pending: [string, string][] = [];
  for (let i = 0; i < agreed.length; i++) {
    for (let j = i + 1; j < agreed.length; j++) {
      const key = [agreed[i].id, agreed[j].id].sort().join('-');
      if (!completedSet.has(key)) {
        pending.push([agreed[i].id, agreed[j].id]);
      }
    }
  }
  return pending;
}

export function computeRankings(
  rankedQuotes: RankedQuote[],
  wins: Record<string, number>
): RankedQuote[] {
  return [...rankedQuotes]
    .sort((a, b) => (wins[b.id] || 0) - (wins[a.id] || 0))
    .map((q, i) => ({ ...q, rank: i + 1 }));
}
```

**Total matchup count for N agreed quotes:** `N*(N-1)/2` — e.g., 5 quotes = 10 matchups. This is fine for typical issue size (3-8 agreed quotes). If a user agrees with all 10 quotes in a 10-quote issue, that's 45 matchups — still tractable but worth noting in the plan.

Reference shows side-by-side cards (`display: flex, gap: 16`). On narrow mobile this works but cards become small. Options:
- Side-by-side with reduced padding (works at 320px+ if cards are compact)
- Stacked with "VS" divider between them (more readable on small screens)

### Anti-Patterns to Avoid

- **Removing `rankedQuotes` as source of truth:** Keep `rankedQuotes` in the store. The `rank` field on each `RankedQuote` should be recalculated from wins before storing, so results and alignment scoring still work unchanged.
- **Storing `completedPairKeys` as a `Set` in Zustand:** `Set` is not JSON-serializable for `persist` middleware. Store as `string[]` (array of pair keys). Convert to `Set` only inside `getPendingMatchups`.
- **Injecting raw `<style>` blocks:** The reference uses a large `<style>` tag at the bottom. In the TypeScript codebase, define keyframes in `index.css` (where all other custom animations live) and reference them via class names or Framer Motion `animate` props.
- **Applying screen shake to `<body>` transform:** The reference animates `transform` on the root div. In React this causes layout thrash for fixed-position elements. Use a wrapper div inside `<main>` with `overflow: hidden` + a ref-driven class toggle instead.
- **Randomized loser shatter positions calculated at render:** The reference uses `Math.random()` in JSX (re-randomizes on every render). Store shard positions in a `useRef` initialized once on component mount.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Ranked list reorder animation | Manual CSS position tracking | Framer Motion `layout` prop | `layout` automatically animates position changes when `rankedQuotes` array order changes |
| Matchup card enter/exit | Custom mount/unmount state | `AnimatePresence` + `motion.div` | Handles unmount animations (loser fade, card replacement) cleanly |
| Winner badge spring | requestAnimationFrame loop | Framer Motion spring transition | `transition: { type: 'spring', stiffness: 400 }` on initial/animate gives slamDown feel |
| Pair key uniqueness | Custom hash function | `[id1, id2].sort().join('-')` | Sorting ensures A-B and B-A produce the same key (reference approach, correct) |

## Common Pitfalls

### Pitfall 1: Store version not bumped
**What goes wrong:** Users with Phase 87 localStorage have `rankedQuotes` without matchup fields (`matchupWins`, `completedMatchupPairs`, `activeMatchupPair`). The app crashes or silently ignores matchup state on resume.
**Why it happens:** Zustand `persist` deserializes old state into new interface shape — missing fields are `undefined`.
**How to avoid:** Bump `version` to `4` in the persist config. The existing `migrate` function wipes to initial state — this is correct behavior (returning users restart the issue).
**Warning signs:** TypeScript errors on `progress.matchupWins` being `undefined` at runtime.

### Pitfall 2: Matchup pair ordering not canonical
**What goes wrong:** Pair `[A, B]` and pair `[B, A]` treated as different pairs — user sees duplicate matchups.
**Why it happens:** Pair key not sorted before joining.
**How to avoid:** Always `[id1, id2].sort().join('-')` when generating and checking keys. Test with IDs that sort lexicographically vs. order of appearance.

### Pitfall 3: Matchup interrupts swipe when only 1 quote agreed
**What goes wrong:** After 1st agree, `getPendingMatchups` returns nothing (correct), but code guard is missing — matchup mode triggers too early.
**Why it happens:** Missing `rankedQuotes.length >= 2` guard before calling `getPendingMatchups`.
**How to avoid:** Guard `switchToMatchup` behind `rankedQuotes.length >= 2` (same pattern as Phase 87's `showInlinePanel` guard).

### Pitfall 4: Rankings sidebar uses stale wins after reorder
**What goes wrong:** `computeRankings` is called with old `matchupWins` before store flush completes.
**Why it happens:** Deriving rankings outside the store without subscribing to wins changes.
**How to avoid:** Derive `rankedQuotes` (sorted by wins) inside a selector or computed in the store action `recordMatchupWin`, so any subscriber gets fresh data.

### Pitfall 5: `Set` in Zustand persist
**What goes wrong:** `completedMatchupPairs` serialized as `{}` (empty object) by JSON.stringify — all pairs appear incomplete after page reload.
**Why it happens:** `Set` is not JSON-serializable.
**How to avoid:** Store as `string[]`, convert to `Set` only at algorithm call sites.

### Pitfall 6: Mobile matchup cards overflowing
**What goes wrong:** Side-by-side cards at 50% width on a 320px screen with padding = ~130px per card. Quote text overflows or wraps to 8+ lines.
**Why it happens:** No `min-width: 0` on flex children, or card padding too large for mobile.
**How to avoid:** `flex: 1; min-width: 0; overflow: hidden` on each card. Limit quote text to 3 lines via `-webkit-line-clamp: 3`. Reduce card padding on mobile breakpoint.

### Pitfall 7: Screen shake animation breaks fixed-position overlay elements
**What goes wrong:** The SiteHeader and any fixed modals shake with the main content.
**Why it happens:** `transform` on a parent creates a new stacking context — `position: fixed` children are now relative to the transformed ancestor, not the viewport.
**How to avoid:** Apply screen shake only to the evaluation content wrapper, not to `<body>` or the full page. The header is outside `<main>`, so it's unaffected if shake is scoped to the `EvaluationPhase` container div.

```typescript
  // ... existing fields unchanged ...
  matchupWins: Record<string, number>;      // quoteId -> win count (default: {})

}
```

### recordMatchupWin store action
```typescript
recordMatchupWin: (winnerId: string, loserId: string) => void;
// Implementation:
recordMatchupWin: (winnerId, loserId) => {
  const state = get();
  const issueId = state.currentIssueId;
  if (!issueId) return;
  const progress = state.issueProgress[issueId];
  const pairKey = [winnerId, loserId].sort().join('-');
  const newWins = { ...progress.matchupWins, [winnerId]: (progress.matchupWins[winnerId] || 0) + 1 };
  const newCompleted = [...progress.completedMatchupPairs, pairKey];

  // Recompute rankedQuotes order by wins
  const reranked = [...progress.rankedQuotes]
    .sort((a, b) => (newWins[b.id] || 0) - (newWins[a.id] || 0))
    .map((q, i) => ({ ...q, rank: i + 1 }));

  // Find next pending matchup
  const pending = getPendingMatchups(reranked, newCompleted);

  set({
    issueProgress: {
      ...state.issueProgress,
      [issueId]: {
        ...progress,
        matchupWins: newWins,
        completedMatchupPairs: newCompleted,
        rankedQuotes: reranked,
        activeMatchupPair: pending.length > 0 ? pending[0] : null,
      },
    },
  });
},
```

## Open Questions

1. **Maximum matchup count UX concern**
   - What we know: 5 agreed quotes = 10 matchups; 8 agreed = 28; 10 agreed = 45
   - What's unclear: Does user feel fatigued at 20+ matchups mid-evaluation? The reference has 5 quotes (10 matchups max) which feels energetic. More quotes = much more matchup work.
   - Recommendation: Planner should consider a matchup cap (e.g., max 6 agreed quotes triggers matchup = max 15 matchups) OR only run matchups at end (batch mode). The reference runs matchups immediately after each agree that creates new pairs — this is more interactive but potentially fatiguing. Worth defining the cap in the plan.

2. **Mobile matchup card layout**
   - What we know: Side-by-side works if cards are compact; reference uses side-by-side
   - What's unclear: At 320px width with 16px total gap + padding, each card is ~144px wide — workable but tight for quote text
   - Recommendation: Plan should specify 2-line clamp on matchup card quote text (vs. full text in swipe card)

3. **Loser animation complexity**
   - What we know: Reference does a "shatter" (8 random fragments fly apart) + `opacity: 0` on the card
   - What's unclear: Whether shatter is worth implementing vs. simpler scale(0.7) + opacity(0) exit
   - Recommendation: Implement simple scale/fade-out first (Framer Motion exit variant), shatter can be added as enhancement. The `CHOSEN` winner badge is the high-value animation.

4. **`pendingRankQuoteId` retention or removal**
   - What we know: Phase 87 uses `pendingRankQuoteId` for drag-rank; this phase replaces that flow
   - What's unclear: Whether to remove the field or leave it dormant
   - Recommendation: Leave dormant in this phase (avoid store churn); mark for removal in Phase 91 cleanup.
