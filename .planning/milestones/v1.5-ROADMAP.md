### Phase 32: CompassV2 Integration Guide

**Goal:** The CompassV2 team has a single, authoritative reference document covering auth, API endpoints, tier access, jurisdiction, and platform philosophy — replacing the outdated COMPASS_CONTRACT.md.
**Depends on:** Nothing (documentation, no code dependency)
**Plans:** 1 plan

Plans:

- [x] 32-01: Write docs/COMPASSV2-INTEGRATION.md (ground-up rewrite of COMPASS_CONTRACT.md)

**Details:**

Delivered `docs/COMPASSV2-INTEGRATION.md` — 745-line ground-up integration guide. `COMPASS_CONTRACT.md` deleted.

10-section structure established as integration guide standard:
1. Quick Reference (endpoint table)
2. Platform context and tier model
3. Auth redirect flow with TypeScript examples
4. Compass reads (topics, answers, categories)
5. Compass writes (answer upsert, batch, selected topics)
6. Profile reads (account/me shape, tier detection)
7. Jurisdiction — "never ask for address" (first-class section)
8. Anonymous → Connected migration (localStorage import)
9. Error codes reference
10. Integration checklist (12 items)

All 6 CDOC requirements satisfied. 8 inline anti-pattern blockquotes placed at exact point of relevance (not consolidated at bottom). 16-endpoint table with TypeScript interfaces for request/response shapes.

Key decisions:
- COMPASS_CONTRACT.md hard-deleted (no symlink) — it documented the wrong auth pattern (direct POST /auth/login)
- Hash fragment rationale included verbatim — frontend devs frequently implement this wrong
- Jurisdiction as Section 7 (first-class) — "never ask for address" is a platform design principle, not an API detail
- Anti-patterns at point of relevance — an AI consuming the guide encounters the warning at the moment of the relevant implementation decision

### Phase 33: Essentials Integration Guide

**Goal:** The Essentials team has a reference document covering the Inform Pillar access pattern, the "never ask address again" jurisdiction principle, and how to surface Connected enhancements as opt-in.
**Depends on:** Nothing (documentation, no code dependency; parallel to Phase 32)
**Plans:** 1 plan

Plans:

- [x] 33-01: Write docs/ESSENTIALS-INTEGRATION.md (new file)

**Details:**

Delivered `docs/ESSENTIALS-INTEGRATION.md` — 654-line canonical integration reference for the Essentials team.

Core patterns documented:
- Three-branch `detectUserState()` returning typed union: `inform | connected_with_jurisdiction | connected_no_jurisdiction`
- "Inform is the unconditional baseline" — Essentials must be fully functional for anonymous users; Connected is additive, never gating
- All 10 jurisdiction fields with TIGER/Line GEOID formats and real production examples
- Auth redirect flow matching CompassV2 pattern
- Service-to-service XP/gem award endpoints with `X-Service-Key` header
- Deterministic idempotency key format: `{app}:{action}:{user_id}:{context}`

All 6 EDOC requirements satisfied. `Jurisdiction` interface verified against actual `GET /api/account/me` output.

Key decisions:
- Never prompt for location consent — accounts app owns location consent exclusively; Essentials reads jurisdiction if present, shows address input if null
- Connected-without-jurisdiction treated same as Inform for location UI — but XP/gem awards still available
- Numeric TIGER/Line GEOIDs — `"1807"` for Indiana's 7th, `"18030"` for Indiana Senate District 30
- Service key provisioning is operational (not a code blocker) — implementation documents the pattern; keys provisioned separately
