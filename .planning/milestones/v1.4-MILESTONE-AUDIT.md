## E2E Flow Verification

### Flow 1: Alpha User Views Profile

1. User logs in -> App.tsx fetches /account/me -> stores tier/email in authStore
2. User navigates to /profile -> AuthGuard passes (authenticated)
3. ProfilePage mounts -> fetches /account/me
4. /account/me reads connected_profiles (verification_rating, vq_hold_until, total_xp, gem balances)
5. /account/me calls calculate_level RPC -> returns level/xp breakdown
6. Response includes verification_rating at root and inside connected_profile
7. ProfilePage renders tier badge, Level, XP, Gems (yellow/blue/red), VR as X / 150
8. If vq_hold_active -> red VQ hold active warning displayed
9. Feature hub renders 6 cards unconditionally (visible to all tiers)
10. If location_consent -> /account/me/jurisdiction fetched -> Civic Spaces pills rendered

**Status: COMPLETE** -- all 10 steps verified in code.

### Flow 2: VQ Confirms a Stance

1. VQ app sends POST /api/vq/confirm-stance with service key + payload
2. requireGemServiceKey validates key from GEMS_SERVICE_KEYS env var
3. Route validates red in permittedGemTypes
4. Zod validates request body (politician_id, topic_id, confirmed_value, user arrays, idempotency_key, gems_amount)
5. confirmVqStance() calls adminRpc(confirm_vq_stance) with all 7 params
6. RPC: pre-check vq_confirmation_results for idempotency replay (before any lock or write)
7. RPC: SELECT FOR UPDATE on connected_profiles for all users (sorted UUID order, deadlock prevention)
8. Correct users: INSERT gem_transaction + UPDATE gem_balance_red + LEAST(vr+3, 150) VR
9. Incorrect users: GREATEST(vr-10, 0) VR + CASE vq_hold_until when vr hits 0
10. Upsert inform.politician_answers with confirmed_value
11. Cache result in vq_confirmation_results
12. Return JSON with user results, counts, unresolved_users

**Status: COMPLETE** -- live-tested 2026-03-17T02:09:28Z: new_rating:63 (+3), gems_awarded:1, replayed:true on replay

### Flow 3: Admin Overrides Verification Rating

1. Admin navigates to /admin/accounts/:userId (AdminGuard protects route)
2. AccountDetailPage fetches account data -- includes connected_profile.verification_rating and vq_hold_until
3. VR section renders in Admin-Only Fields card with status badges
4. Admin clicks Edit -> vrEditMode state activates, vrDraft initialized from current values
5. Admin modifies rating (range 0-150 enforced; save disabled + error if out-of-range)
6. Admin optionally clicks Clear Hold -> vrDraft.clearHold = true
7. Admin clicks Save -> apiFetch PATCH /admin/accounts/:userId/verification-rating
8. Route validates via Zod refine (must provide rating or clearHold)
9. updateVerificationRating() updates connect.connected_profiles via supabaseAdmin
10. logAdminAction() writes update_verification_rating audit entry
11. 200 returned -> vrEditMode(false) + fetchAccount() refreshes page

**Status: COMPLETE** -- 8/8 verification truths confirmed in Phase 29 report.

### Flow 4: CTC Game Awards XP + Yellow Gem

1. CTC sends POST /api/xp/award with TRIVIA_SERVICE_KEY + user_id + amount + idempotency_key
2. XP route validates service key
3. award_xp RPC: updates total_xp on connected_profiles, writes xp_transactions entry
4. Returns total_xp, level, is_duplicate
5. CTC sends POST /api/gems/award (yellow) with same service key
6. Gem route validates key + yellow in permittedGemTypes
7. credit_gems RPC: updates gem_balance_yellow, writes gem_transactions entry

**Status: COMPLETE** -- live-tested 2026-03-17T02:09:28Z: total_xp 1996->2096, is_duplicate:false, replay confirmed

## Profile Hub UI: Admin Tool vs. End-User Frontend

The Phase 30 Profile Hub is built in admin/src/pages/ProfilePage.tsx and served at /profile on the admin tool domain. It is NOT a separate end-user frontend.

Key points:

- The page is accessible to any authenticated user (any tier), not just admins. AuthGuard (not AdminGuard) protects the route -- this is correct, it is the user own profile view.
- The admin React app at admin/src/ serves dual purpose: /admin/* routes are admin-only; /profile, /login, and /signup are general-purpose authenticated routes.
- The production end-user frontend (Framer) is a separate app not in this repo.
- Alpha users access their profile at https://accounts.empowered.vote/profile (the admin tool domain).

This is the intended design for Alpha, explicitly confirmed in 30-RESEARCH.md.

Tech debt note: The admin app serving dual purpose creates a long-term separation-of-concerns concern. For Alpha this is acceptable. For production, the profile page should migrate to the Framer frontend or a dedicated user-facing frontend. This is a known architectural decision, not a defect.

## Notable Findings

### 1. VQ-02 spec vs. implementation (minor discrepancy, no functional impact)

REQUIREMENTS.md VQ-02 states gems are awarded via existing credit_gems RPC. The actual Migration 038 implementation does NOT call credit_gems -- it does gem INSERT + balance UPDATE inline. Phase 28 SUMMARY explicitly documents this decision: nested SECURITY DEFINER calls are unreliable in Postgres. The requirement (gems awarded to correct users) is fully satisfied. Spec language is imprecise. No fix needed.

### 2. Feature hub URL deviation from plan (cosmetic, user-approved)

Phase 30 Plan 02 specified placeholder URLs like https://choose-the-correct.empoweredvote.com. ProfilePage.tsx uses production-style URLs like https://ctc.empowered.vote. Phase 30-02 SUMMARY notes this was accepted during live review. No action required.

### 3. 6 feature hub cards vs. 5 required (exceeds requirement, user-approved)

PROFILE-03 requires 5 cards. ProfilePage.tsx renders 6 (adds Empowered Compass). Phase 30-02 SUMMARY marks this as deviation: 6th card added per user request during review. No action required.

### 4. INTEG-01 and INTEG-02 live test completion post-dates REQUIREMENTS.md

Phase 29 automated verification (2026-03-15) correctly marked INTEG-01/02 as HUMAN_NEEDED pending Render env var configuration. Live tests were run 2026-03-17T02:09:28Z and both passed. Results are recorded in Phase 29 VERIFICATION.md front matter (live_tested field). REQUIREMENTS.md was never updated to reflect this. Update needed before archiving.

### 5. CTC gem awards bypass accounts API (known gap, pre-existing)

CTC credit_gems calls connect.credit_gems RPC directly via service role, bypassing the accounts API. Documented in MEMORY.md as a known gap from a previous milestone. Not a v1.4 issue.
