# Milestone v1.1: XP & Progression

**Status:** ✅ SHIPPED 2026-03-04
**Phases:** 9–11
**Total Plans:** 5

## Overview

Add a unified XP and leveling system — append-only ledger, atomic award RPC, tiered level calculation, public XP profile endpoint, and admin ledger view — so any feature repo can read and award XP with idempotency guarantees. XP is a permanent civic participation record: no decay, no expiry, no pay-to-win.

## Phases

### Phase 9: XP Schema & Core

**Goal:** The XP ledger and level calculation exist in the database and are enforced by RLS — the infrastructure every upstream phase depends on.
**Depends on:** Phase 8 (v1.0 complete)
**Requirements:** XPLED-01, XPLED-02, XPLED-03, XPLED-04, XPLED-05, LEVEL-01, LEVEL-02
**Plans:** 2 plans

Plans:

- [x] 09-01-PLAN.md — XP schema migration (xp_transactions table, connected_profiles columns, view update, RLS, grants)
- [x] 09-02-PLAN.md — calculate_level + award_xp RPC functions and SQL test file

**Success Criteria (met):**

1. A Connected user's XP award is persisted atomically — both the ledger row and the denormalized `total_xp` / `current_level` on `connected_profiles` update in the same transaction or neither updates.
2. Calling `award_xp` twice with the same idempotency key inserts exactly one ledger row — the second call is a silent no-op, not an error.
3. A Connected user querying `xp_transactions` via Supabase RLS sees only their own rows; an unauthenticated query returns zero rows.
4. Level progression follows the defined thresholds (2k × 3, 3k × 6, 4k × 20, 5k thereafter), and `xp_in_level` plus `xp_to_next_level` are computable from any `total_xp` value.

**Key decisions:**

- `connect.xp_transactions` append-only with UNIQUE `idempotency_key` — mirrors gem_transactions pattern
- `total_xp` stored as BIGINT (not INT) — prevents overflow for high-volume users
- Legacy `xp` column on `connected_profiles` intentionally preserved — Phase 10 handles migration/removal
- No write RLS policies on `xp_transactions` — all writes via `award_xp()` SECURITY DEFINER RPC only
- `anon` GRANT SELECT with no anon RLS policy → returns empty set, not permission denied
- `xp_in_level` and `xp_to_next_level` computed on read, not stored as columns
- `calculate_level` uses `LANGUAGE sql` (not plpgsql) — IMMUTABLE qualifier enables Postgres caching/inlining
- `calculate_level` GRANTed to anon — Phase 10 public XP endpoint needs it unauthenticated
- `award_xp` idempotency duplicate returns current profile state (not historical state at original award time)
- `award_xp` uses `RETURNS TABLE` to mix xp_transactions fields, calculate_level output, and `is_duplicate` flag

### Phase 10: XP API

**Goal:** Feature repos and authenticated users can read and award XP through the Express API — with idempotency enforcement, source validation, and XP data surfaced on the account/me response.
**Depends on:** Phase 9
**Requirements:** XPAPI-01, XPAPI-02, XPAPI-03, XPAPI-04, XPAPI-05, XPAPI-06
**Plans:** 2 plans

Plans:

- [x] 10-01-PLAN.md — xpService module, service-key middleware, POST /api/xp/award with source validation and idempotency
- [x] 10-02-PLAN.md — GET /api/xp/:userId, GET /api/xp/me/history, GET /account/me XP object extension, integration tests

**Success Criteria (met):**

1. A feature repo calling `POST /api/xp/award` with a valid `X-Service-Key` and a new idempotency key receives a 200 with the created transaction; repeating the same call returns 200 with the original transaction and no second ledger row.
2. Calling `POST /api/xp/award` with an unrecognized source type is rejected with a 422 — the award is never written.
3. `GET /account/me` for a Connected user includes an `xp` object containing `total`, `level`, `xp_in_level`, and `xp_to_next_level`.
4. `GET /api/xp/:userId` returns `{ level, total_xp, xp_in_level, xp_to_next_level }` to an unauthenticated caller without exposing the full transaction ledger.
5. `GET /api/xp/me/history` for an authenticated Connected user returns the caller's ledger entries (source, amount, metadata, created_at); an unauthenticated request is rejected with 401.

**Key decisions:**

- Service keys optional in Zod env schema — avoids breaking integration tests that don't set service key env vars
- `SERVICE_KEY_MAP` built at module load time (not per-request) — env vars static after process launch
- Per-key source authorization returns 422 (not 403) — valid key + unauthorized source = caller usage error
- `XP_SOURCES` const array satisfies both `z.enum(XP_SOURCES)` and `typeof XP_SOURCES[number]` — single source of truth
- `award_xp` RPC row fields `id` and `current_level` remapped to `transaction_id` and `level` in `AwardXpResult`
- Legacy `xp` column used for `calculate_level` input in account.ts — `total_xp` not yet in generated types; same value
- `(supabaseAdmin as any)` escape for xp_transactions table and total_xp column in xpService.ts — pending supabase gen types re-run
- Route order enforced in xp.ts: `GET /me/history` before `GET /:userId` — test guards permanently
- `adminRpc` for IMMUTABLE `calculate_level` in route handler — architecture test checks for string `supabaseAdmin` only

### Phase 11: Admin Tool XP View

**Goal:** Admins can inspect any Connected user's XP standing and full transaction history from the existing account detail page without leaving the admin tool.
**Depends on:** Phase 10
**Requirements:** XPADM-01, XPADM-02
**Plans:** 1 plan

Plans:

- [x] 11-01-PLAN.md — Backend XP history endpoint + admin UI XP summary header and XP History section

**Success Criteria (met):**

1. The account header in the admin tool displays a Connected user's total XP and current level alongside existing account summary fields.
2. Admin can navigate to an XP History tab on any Connected account detail page and see every ledger entry — source, amount, metadata, and timestamp — in reverse chronological order.

- Metadata expand/collapse with em-dash fallback for null/empty entries

## Milestone Summary

**Decimal Phases:** None — all phases executed in order.

**Key Decisions:**

- XP ledger mirrors gem ledger: append-only rows, denormalized balance, advisory lock in RPC — consistent pattern across all ledger types in the system
- `calculate_level` as IMMUTABLE SQL function: LANGUAGE sql enables Postgres caching; CTE pattern handles all 4 tier boundaries cleanly
- Single write path: `connect.award_xp` is the only way to award XP — no application-layer direct inserts to xp_transactions ever
- Idempotency at DB layer: UNIQUE constraint + RPC pre-check means callers can safely retry on network failure without double-awarding
- `account/me` XP shape breaking change: replaced legacy integer field with structured `{ total, level, xp_in_level, xp_to_next_level }` — CompassV2 frontend breaking change accepted

**Issues Resolved:**

- calculate_level column name bug: TypeScript callers used `.current_level` instead of `.level` — silent zero-level bug caught and fixed during milestone audit (affected getPublicXpProfile and account/me XP level)
- Route order collision: `GET /me/history` must be registered before `GET /:userId` — Express param routes match before literals; permanent test guard added

**Issues Deferred:**

- supabase gen types not re-run: xp_transactions and total_xp still require `(supabaseAdmin as any)` type escape until gen types is executed after migrations apply
- SQL test suite execution blocked: Docker not installed on dev machine; 12-test suite ready and waiting for `supabase db reset`
- Missing test coverage: valid service key + unauthorized source (SOURCE_NOT_PERMITTED path) not yet covered by integration tests

**Technical Debt Incurred:**

- D-XP-READ-01: `account.ts` reads legacy `xp` column (not `total_xp`) for calculate_level input — unify when supabase gen types is re-run
- D-XP-READ-02: `(supabaseAdmin as any)` in xpService.ts for xp_transactions and total_xp — clear when supabase gen types is re-run after Phase 9 migrations apply
