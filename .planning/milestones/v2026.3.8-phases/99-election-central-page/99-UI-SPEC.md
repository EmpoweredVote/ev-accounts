## Visual Hierarchy

The Elections view has two levels of visual anchor:

- **Primary focal point:** The candidate card grid. Cards are the densest information unit and the primary interactive element — the eye leads here first within any election section.
- **Secondary anchors:** Election section headers (election name + date + countdown). These establish context and separating rhythm between multiple elections. They are visually subordinate to the card grid but serve as the structural skeleton of the page.

Source: CONTEXT.md D-05, D-07, D-08; layout intent of CategorySection + PoliticianCard pattern.

## Tab Toggle Specification

The tab toggle sits at the top of the Results page, below the address search input and above the results content.

**Visual treatment:**
- Two tabs: "Representatives" and "Elections"
- Rendered as `<button>` elements in a flex row with a bottom-border track
- Inactive tab: text color `#718096` (textMuted), no underline, font-weight 400
- Active tab: text color `#00657C` (evMutedBlue), 2px bottom border in `#00657C`, font-weight 600
- Hover (inactive): text color `#4A5568` (textSecondary)
- Tab height: 44px minimum (touch target)
- Tab horizontal padding: 16px each side
- Bottom border track: 1px solid `#E2EBEF` (borderLight) spanning full width

**Dot indicator:**
- 8px × 8px filled circle, background `#00657C`
- Positioned inline to the right of the "Elections" label, 4px gap
- Hidden (display: none) during loading state and when elections array is empty
- Visible only after elections fetch completes and returns at least one election

**URL state:**
- Active tab driven by `?view=` search param: `representatives` (default, omit param) or `elections`
- Tab switch uses functional `setSearchParams` to preserve the `?q=` address param
- Source: CONTEXT.md D-02, RESEARCH.md Pattern 1

## Election Header Specification

Each election rendered in the Elections view gets its own header block before its tier sections.

**Layout:** Full-width block, background `#FFFFFF`, border-bottom `1px solid #E2EBEF`, padding `16px 24px` on desktop, `8px 16px` on mobile.

**Text content:** `{election_name} · {formatted_date}[ · {N} days away]`

- `election_name`: as returned by API (e.g., "2026 Indiana Primary")
- `formatted_date`: `Month D, YYYY` format (e.g., "May 6, 2026")
- `days away`: appended only when days until election < 60. Integer days, no decimal.
- Typography: 16px / weight 600 / `#00657C`

**Timezone note:** Parse election dates as `dateStr + 'T12:00:00'` to avoid UTC midnight boundary issues. See RESEARCH.md Pitfall 5.

Source: CONTEXT.md D-07; RESEARCH.md `formatElectionHeader` code example.

## Candidate Card Grid

Cards use `variant="vertical"` from PoliticianCard. Grid layout mirrors the CategorySection built-in grid (`auto-fill, minmax(250px, 1fr)`).

**Responsive breakpoints:**
- Mobile (< 640px): single column
- Tablet (640–1023px): 2 columns
- Desktop (≥ 1024px): 3 columns

**Card content (top to bottom):**
1. Photo (square, rounded) — fallback: initials circle in `#00657C` background, white initials text
2. Candidate full name — 14px / weight 600 / `#1C1C1C`
3. Position name (race title) — 14px / weight 400 / `#4A5568`
4. "Incumbent" label — 12px / weight 600 / `#00657C` — rendered for incumbents only via CSS override on subtitle

**Card interaction:** Full card is clickable, navigates to `/candidate/{candidate_id}`. Cursor: pointer. Hover: subtle background shift to `#F0F8FA` (bgLight).

Source: CONTEXT.md D-05, D-06, D-13; RESEARCH.md Pattern 5 and Open Question 3 resolved as vertical variant.

## Loading State Specification

Loading skeleton is shown while the elections fetch is in flight (after tab click, before data arrives).

**Skeleton pattern:** Mirrors existing `SkeletonSection` in Results.jsx — Tailwind `animate-pulse` on gray-200 placeholder blocks.

**Skeleton structure per section:**
- One `h-4 bg-gray-200 rounded w-24 mb-4` block (section heading placeholder)
- Three inline rows: `w-16 h-16 rounded-full bg-gray-200` (photo circle) + two text lines `h-4 bg-gray-200 rounded` and `h-3 bg-gray-200 rounded`

**Count:** Render two SkeletonSection blocks while loading (one for Local, one for State — assumes most searches return local data first).

Source: CONTEXT.md "Claude's Discretion" — loading skeleton design; RESEARCH.md Lazy-load pattern.

## Empty State Specification

Shown when the elections fetch returns an empty array.

**Layout:** Centered vertically and horizontally within the Elections tab content area, minimum height 240px.

**Visual:**
- No icon
- Heading: 16px / weight 600 / `#00657C`
- Body copy: 14px / weight 400 / `#4A5568`
- No CTA button (coverage is read-only, no user action available)

Source: CONTEXT.md D-12 (locked copy).

## Interaction & State Contracts

| Trigger | State Change | Visual Result |
|---------|-------------|---------------|
| User clicks Elections tab | `?view=elections` added to URL params; address param preserved | Elections tab becomes active (underline, bold); Representatives content unmounts; Elections content mounts |
| Elections tab mounts, no prior data for current address | `electionsLoading = true` | Loading skeleton renders; dot indicator hidden |
| Elections fetch resolves with data | `electionsData = elections[]`, `electionsLoading = false` | Election sections render; dot indicator appears |
| Elections fetch resolves empty | `electionsData = []`, `electionsLoading = false` | Empty state renders; dot indicator stays hidden |
| User clicks Representatives tab | `?view` param removed or set to `representatives` | Representatives content re-renders; Elections content unmounts |
| User submits new address search | `electionsData` reset to null; `electionsLoading` set to false | On next Elections tab visit, data re-fetches fresh for new address |
| User clicks candidate card | Navigate to `/candidate/{candidate_id}` | Profile page loads |

Source: CONTEXT.md D-01 through D-14; RESEARCH.md Lazy-load pattern and Pitfall 3.

## Antipartisan Enforcement

Per established project mission (CLAUDE.md, REQUIREMENTS.md out-of-scope table):

- No party affiliation label rendered anywhere on the Elections tab or candidate cards
- `primary_party` field on `ElectionRace` (present in API for primary election filtering only) is never displayed in the UI
- Candidate ordering within each race is seeded random per user session to prevent position bias

Source: CONTEXT.md D-11; REQUIREMENTS.md Out of Scope table; RESEARCH.md Pattern 4.
