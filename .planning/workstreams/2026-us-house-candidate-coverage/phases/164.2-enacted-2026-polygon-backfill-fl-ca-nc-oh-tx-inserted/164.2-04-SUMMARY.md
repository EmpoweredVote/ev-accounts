## Decisions Made
- **Party encoding:** stored spelled-out `Democratic`/`Republican` (matching FL incumbents) + `NPA` for Gist (Florida's official no-party term), rather than the plan's shorthand `'D'`. A lone single-letter party value among a DB of spelled-out parties would be a data-quality regression; party is never shown on the candidate card regardless.
- **external_id band** derived empirically from live FL rows: `-(1210000 + district*100 + seq)` — the generic Wave-1 `-(fips*10000+cd*100+seq)` formula did not match the live data.

## Deviations from Plan

### Auto-fixed Issues

**1. [Correctness — Blocking] CA-1 UPDATE referenced target table inside a FROM-join ON**
- **Found during:** Task 3 (first apply of migration 1382)
- **Issue:** `UPDATE ... FROM ... JOIN politicians p ON p.id = rc.politician_id` is invalid Postgres (cannot reference the UPDATE target `rc` in a FROM join). The BEGIN/COMMIT wrapper rolled the whole migration back atomically (no partial writes).
- **Fix:** Moved politician resolution to a scalar subquery on `rc.politician_id`; re-ran the idempotent migration successfully.
- **Files modified:** backend/migrations/1382_fl_add_candidates_and_ca1_gallagher.sql
- **Verification:** re-apply printed INSERT 0 7 / INSERT 0 7 / UPDATE 1 / COMMIT; all Task-3 verify queries pass.
- **Committed in:** fb1ef908

**2. [Convention] Plan verify literals corrected (cosmetic — DB state is correct)**
- **Issue:** Task-2 automated verify greps `p.party='D'` and `is_active=...|f`. Actual state stores `party='Democratic'` (DB convention) and psql renders the boolean as `false`.
- **Fix:** Ran equivalent checks (`party='Democratic'`, output `Daniel Webster|false`) — both confirm correct state.
- **Impact:** none on data; only the plan's literal grep strings were off.
