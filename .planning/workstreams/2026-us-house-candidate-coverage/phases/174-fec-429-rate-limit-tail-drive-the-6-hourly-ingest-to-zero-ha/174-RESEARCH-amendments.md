# Phase 174 — Supplemental Research: Incremental Schedule A Fetching (Amendment-Aware)

**Researched:** 2026-07-23
**Domain:** FEC OpenFEC API (`api.open.fec.gov`) — Schedule A itemized-contribution incremental refresh
**Confidence:** HIGH on the mechanism (live-verified), MEDIUM on universal generalization of amendment→load_date behavior (spot-checked, not exhaustively proven), LOW on nothing load-bearing left unverified

**Relationship to `174-RESEARCH.md`:** That document addresses *pacing* the existing request volume (caching, backoff, shared limiter) under the 1,000/hr ceiling. This document addresses a different, complementary lever: **cutting the request volume itself at the root** by no longer re-pulling each committee's whole 2-year history every run. Both should ship together for FEC-01..04 to reach zero-429 with headroom.

---

## 1. Verified Answer to the Core Question

**Headline: YES — the FEC API can fetch only new + amended Schedule A rows incrementally, via `min_load_date`/`max_load_date` on `/v1/schedules/schedule_a/`, confirmed live on today's data. It also already gives amendment-resolved (current-version-only) records, which is exactly what the free bulk loader cannot do.**

| # | Question | Verdict | Evidence |
|---|----------|---------|----------|
| 1 | `min_load_date`/`max_load_date` exist on `/v1/schedules/schedule_a/` | **VERIFIED** | Fetched FEC's live OpenAPI spec (`https://api.open.fec.gov/swagger/?format=openapi`) — `schedule_a` GET parameter list includes `min_load_date`, `max_load_date` verbatim. Confirmed functionally: a live call with `committee_id=C00908079&min_load_date=2026-07-20` returned only 18 rows (all `load_date=2026-07-22...`) versus that committee's much larger full-cycle history — the filter measurably narrows results. Also confirmed the filter works with NO `committee_id` at all (FEC-wide): `min_load_date=2026-07-22&max_load_date=2026-07-23` → `count: 335,261` (system-wide daily Schedule A load volume, all filers). Date format is **date-only** (`YYYY-MM-DD` or `MM/DD/YYYY`) — a live 422 test proved `min_load_date=2026-07-23T12:00:00` is rejected (`"Date must be formatted as MM/DD/YYYY or YYYY-MM-DD"`). **There is no hour-level granularity.** |
| 2 | Amendment ⇒ `load_date` updates, so incremental pulls capture amendments | **VERIFIED (empirically, on real live data), with one open generalization gap** | Live example: committee `C00811166`, an FEC-confirmed amended filer (found via `/v1/filings/?amendment_indicator=A&form_type=F3X`, `previous_file_number=1962170`). Querying `committee_id=C00811166&min_date=2026-03-26&max_date=2026-03-26` (no load_date filter) returns exactly **3** current Schedule A rows for that date (a $1,000,000, a $5,000, and a $5,000 contribution) — each with `amendment_indicator:"A"`, `file_number:1962170`, and **`load_date:"2026-07-23T03:05:58"`** (today, i.e. very recently re-touched even though the underlying `contribution_receipt_date` is from March). No duplicate/stale row for the same contribution was found — the API returned exactly one current version per transaction, no old-vs-amended pair. This is the key contrast with the bulk file (which the loader's own doc comment says keeps *both* SUB_IDs): **the live API serves only the current version of each transaction; superseded originals do not persist as separate rows returned by the query.** `original_sub_id` (confirmed present in the `ScheduleA` OpenAPI schema — `{"type":"string"}`) is the linking field FEC uses when a new SUB_ID supersedes an old one, though in the ~1,500 rows sampled this session it was always `null` (most transactions are never amended, so this is expected, not contradictory). **Gap:** I was not able to catch a *live* row with `original_sub_id` populated in the sampling budget available this session (several high-volume committees and multiple freshly-amended filings were tried; none happened to have a Schedule A line that was itself a re-amendment of a prior SUB_ID at the moment of testing). The causal mechanism (amendment → fresh `load_date`, no stale duplicate surfaces) is demonstrated on a real case; the `original_sub_id` linkage field's exact supersession semantics are schema-confirmed but not behaviorally observed end-to-end this session. **A human should spot-check one more real `original_sub_id`-populated row before this becomes a locked assumption** (see Assumptions Log). |
| 3 | `/v1/filings/` amendment metadata + `schedule_a` filter by `file_number`/`image_number` | **VERIFIED but NOT RECOMMENDED as the mechanism** | `/v1/filings/` (and `/v1/committee/{id}/filings/`) DOES support `is_amended` (boolean), `amendment_indicator` (N/A/T), `previous_file_number`, and `min_receipt_date`/`max_receipt_date` — confirmed via live OpenAPI param list and a live call (`is_amended=true&form_type=F3X` returned real amended filings with `previous_file_number` populated). However, `/v1/schedules/schedule_a/` does **NOT** accept `file_number` as a filter (confirmed absent from its param list) — only `image_number`/`min_image_number`/`max_image_number`. Chaining filings→schedule_a would require: (a) one `/v1/filings/` call to enumerate amended filings since last run, (b) one `schedule_a` call per resulting `image_number`/committee to pull its lines — strictly more API calls than just filtering `schedule_a` directly by `min_load_date`, for no additional coverage (point 2 already shows `min_load_date` captures the same amendment activity directly on the itemized data). **Recommendation: skip this path entirely** — use `min_load_date` directly on `schedule_a`. |
| 4 | Interaction with existing adapter code (`two_year_transaction_period`, `min_date`/`max_date`, `last_indexes`, `is_amended`/`memo_code='X'` skip) | **VERIFIED, with one bug finding** | `min_load_date`/`max_load_date` compose cleanly alongside the existing params — confirmed live (`committee_id` + `two_year_transaction_period` + `min_load_date` + `sort` + pagination all worked together in the same request in this session's tests). Per-committee iteration (`resolveCommitteeIds` → loop → `streamAllPagesForCommittee`) is **still the right shape** — a global no-`committee_id` query is technically possible (point 1) but returns FEC-wide volume (335K/day) that would need committee-ID filtering client-side across ~3,300 pages/day just to find our ~1,000 tracked committees' rows — far worse than looping our own known committee IDs. **Bug finding:** `shouldSkipRecord`'s `record['is_amended'] === true` check (line ~541) references a field that **does not exist** on the `ScheduleA` response schema — confirmed by dumping the full live OpenAPI `ScheduleA` definition's property list (no `is_amended` field anywhere; only `amendment_indicator`/`amendment_indicator_desc`/`original_sub_id`). This condition is dead code — always `false` — for the schedule_a endpoint. It appears harmless today only because (per point 2) the live API doesn't return stale superseded rows in the first place, so there's nothing for that check to catch. It should either be removed (misleading) or replaced with real amendment-supersession handling (see Design section, below). |
| 5 | Volume estimate: incremental pull vs current full per-source re-pull | **VERIFIED order-of-magnitude, live-measured** | Current architecture: `streamAllPagesForCommittee` pulls the **whole 2-year cycle** per committee per 6h run (fast path is one unbounded query per committee, paginated at 100/page with a 5s sleep between pages) — for ~1,000 tracked committees, most with hundreds to tens-of-thousands of records, this is easily tens of thousands of requests per 6h window, which is the documented cause of the 429 tail. With `min_load_date` scoped to "since last successful run": a committee with zero new/amended activity in the window returns in **1 request** (page 1, `count`/`pagination` show 0 or few results, loop exits). Live example: `C00908079` narrowed from its full-cycle history to 18 rows via a `min_load_date` filter — 1 page. Empirically, most of a fixed committee roster will have zero-to-few new Schedule A lines on any given day outside FEC quarterly filing deadlines. **Estimated steady-state: ~1,000 committees × ~1 request average ≈ 1,000–1,500 requests per full daily sweep**, versus the current architecture's tens of thousands per 6h window — roughly a 10–50× reduction, order-of-magnitude consistent with what's needed to clear the residual 429 tail. |

## 2. Recommended Design for FEC-01 + Schedule A Incremental Refresh

### FEC-01 (committee resolution) — already solved, confirm and lock it in
`fecBulkLoader.ts::buildCommitteeMap` already derives `CAND_ID → committee_id` from the free `ccl{YY}.zip` bulk file (no API call, no rate limit exposure) — read this session, `backend/src/lib/adapters/fecBulkLoader.ts:104-122`. **Recommendation: `resolveCommitteeIds()` in `fecAdapter.ts` should stop calling `/v1/candidates/search/` on the hot path entirely** and instead source committee IDs from the same `ccl` mapping (cache it once per cycle, refresh daily/weekly — committee linkages are near-static within a cycle). This alone removes an entire class of the 429s (`resolveCommitteeIds` was one of the two named failure sites in `174-RESEARCH.md`, and per project memory was responsible for the bulk of the 15k/14d fails before the `d505c9ad` backoff fix).

### Schedule A refresh — replace "whole cycle every run" with "incremental since last run"

1. **Per committee** (keep the existing loop shape — do not switch to the FEC-wide no-`committee_id` query; see point 4):
   - After an initial one-time backfill per (source, cycle) — the existing whole-cycle path, run once, not on every cron tick — subsequent runs call `schedule_a` with `committee_id` + `two_year_transaction_period` + **`min_load_date = <last successful run's watermark, minus a 2-day safety lookback>`**.
   - The 2-day lookback (rather than exactly "last run") absorbs day-boundary/timezone ambiguity in `load_date` and is cheap: `ON CONFLICT (data_source, source_transaction_id) DO UPDATE` already makes re-fetching a couple of overlapping days idempotent.
   - Store the watermark as the max `load_date` actually observed per (source, cycle) pair (or simply "yesterday's date," given day-only granularity — see cadence below), not a wall-clock timestamp of when the job ran.

2. **Amendment supersession — new logic needed, this is the actual "preserve amendment resolution" work:**
   - When a fetched row has `original_sub_id` non-null, the row it supersedes (keyed by `source_transaction_id = original_sub_id`, same `data_source='fec'`) must be retired — either hard-deleted or soft-deleted from `transparent_motivations.contributions` — or the totals will double-count (new amended row inserted via `ON CONFLICT` on the NEW sub_id, old row never touched since its own sub_id no longer appears in any future query). This gap exists **today** in the whole-cycle path too, not just the new incremental path — it is a pre-existing latent bug, surfaced by this research, not something the incremental design introduces. Recommend as its own small task: `DELETE FROM contributions WHERE data_source='fec' AND source_transaction_id = $original_sub_id` (or a soft-delete column, matching the project's existing soft-delete convention) whenever a normalized row carries a non-null `original_sub_id`.
   - Remove (or repurpose) the dead `is_amended` check in `shouldSkipRecord` — it never fires against the real schema; replace its intent with the `original_sub_id` supersession handling above.

3. **Cadence — daily, not 6-hourly, for the Schedule A refresh specifically:**
   `min_load_date`/`max_load_date` have **date-only** granularity (verified, point 1). Running the refresh every 6 hours would re-scan the *same calendar day's* window up to 4 times with zero additional freshness — pure waste of the rate-limit budget for no benefit. **Recommend: run the Schedule A incremental refresh once per day** (e.g., early morning UTC, after FEC's own nightly batch load completes — FEC's public developer docs describe data loading as a nightly/periodic batch process, consistent with the `load_date` timestamps observed this session clustering around `03:05:xx` UTC). At ~1,000–1,500 requests/day with the existing `PER_PAGE_SLEEP_MS=5000` pacing, a full sweep takes roughly 80–125 minutes and averages well under 1,000/hr — comfortably inside the confirmed personal-key ceiling (see below) with slack for FEC quarterly-deadline volume spikes (many committees filing/amending at once).
   - If the product still wants a 6-hourly *heartbeat* for other, non-FEC sources sharing the same cron file, gate the FEC-specific step so it only executes on the day's first invocation (or move it to its own daily-only scheduled entry) rather than re-running the FEC step every tick.

4. **Confirmed rate ceiling (cross-check against `174-RESEARCH.md`'s figure):**
   Deliberately triggered a live 429 (using `DEMO_KEY`, not the production key, to avoid burning prod quota) and captured FEC's own error body verbatim:
   > `"You have exceeded your rate limit of 40 calls per hour for the DEMO_KEY, 1000 calls per hour for a personal key, or 120 calls per minute for an upgraded key."`
   This **confirms** the existing research's 1,000/hr figure for the registered ("personal") key directly from FEC's own server-side error message — the strongest possible confirmation (first-party, live, verbatim). One nuance worth flagging: the `X-RateLimit-Limit`/`X-RateLimit-Remaining` **headers** returned on ordinary 200 responses showed `60` (production key) and `10` (`DEMO_KEY`) — not `1000`/`40`. These headers appear to reflect a shorter rolling sub-window (burst-rate) layer distinct from the hourly cap stated in the 429 body (the `DEMO_KEY` "remaining" value was observed to recover mid-burst, i.e., a sliding window, not a flat per-hour counter). **Do not use the raw header value as "requests per hour" — the authoritative hourly figure is the one in the 429 error body (1,000/hr personal key), matching `174-RESEARCH.md`.** This is noted as a residual open item below since it wasn't fully reconciled this session.

## 3. Residual Risks / Assumptions Needing a Decision

| # | Item | Risk if wrong | What a human should check |
|---|------|----------------|----------------------------|
| A1 | `original_sub_id` supersession semantics (amended row links back to the SUB_ID it replaces) are schema-confirmed (`original_sub_id` field exists on `ScheduleA`) and behaviorally *consistent* with what was observed (no stale duplicate rows for a known-amended committee/date), but a row with `original_sub_id` actually populated was not caught live this session. | If the real semantics differ (e.g., `original_sub_id` is populated for a different reason, or amendment supersession works differently than assumed), the proposed DELETE-on-supersession logic could delete the wrong row or miss the real dedup key. | Before implementing the supersession-delete task, run one more targeted live query (e.g., filter a very high-amendment-volume committee like a national party committee across several `min_load_date` days) until a row with non-null `original_sub_id` is caught, and confirm its `original_sub_id` matches a real prior `sub_id` that was previously returned by the API for that committee. |
| A2 | The X-RateLimit-* header discrepancy (60/10 shown vs. 1,000/40 documented and 429-confirmed) was not root-caused this session. | If the header actually represents a stricter enforced ceiling in some deployment path (e.g., a CDN/API-gateway layer in front of the documented api.data.gov policy), the "80–125 min once-daily sweep" estimate could still trip a shorter-window throttle even though it's under the hourly cap. | Not blocking — the existing code's `PER_PAGE_SLEEP_MS=5000` already paces requests far below even the stricter 60/window reading (5s between requests ≈ 12/min sustained, well under any observed threshold). No action needed unless a future load test shows otherwise. |
| A3 | Whether FEC's nightly batch load window (`load_date` clustering ~03:05 UTC, observed this session on live rows) is a fixed, reliable schedule or coincidental to the small sample pulled. | If the daily refresh is scheduled right before FEC's nightly load completes, it could miss that day's freshly-loaded rows until the next cycle. | Schedule the daily refresh with a safety margin (e.g., run at 06:00 UTC, several hours after the observed ~03:05 UTC load-timestamp cluster) and/or keep the 2-day lookback window as a built-in safety net regardless of exact scheduling. |
| A4 | The dead `is_amended` check in `shouldSkipRecord` — confirmed the field doesn't exist on the live schema today; whether it existed on an older FEC API version (explaining why the code was written this way) was not verified. | Low risk — removing/replacing dead code doesn't change current behavior either way. | None required before proceeding; purely informational for the plan/commit message ("this check was already inert"). |
