# Phase 168.1: Depth-Aware 3-Tier Elections Coverage - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Redefine the admin elections coverage metric from **breadth** (a race is "covered" when `candidate_count > 0`) to **depth** — classify each statewide/legislative race into a coverage tier from three per-candidate signals:

- **Tier 1** — candidate names only
- **Tier 2** — names + (compass **stances** OR **transparent motivations**)
- **Tier 3** — names + stances + transparent motivations
- **Tier 0** — no active candidates at all (below Tier 1; race exists but nobody loaded)

Surface a covered/total-by-tier readout in the `StatewideRacesPanel` (per-race tier + per-tier totals) and repoint the state choropleth fill from the breadth number to a tiered depth score.

**Requirements:** ELEC-04, ELEC-05, ELEC-06 (see the workstream `REQUIREMENTS.md`).

**Builds directly on Phase 168** — extends the `classifyRaces` statewide/legislative split and the `StateElection`/`RaceRow` contract. Inserted at 168.1 (before Phases 169/171/172) so the metric contract stabilizes before the DB-derived core, user-relevant metric, and public API consume the elections signal.

**Explicitly NOT in scope:**
- County/local-pinnable races and the county drill-down — those stay on Phase 168's breadth coverage (`classifyCounty` → `raceCoverage`) untouched; Phases 169 (DB-derived core) and 170 (city drill-down) will overhaul that side, so touching it now is rework risk.
- No changes to the completeness (7-axis) map/metric.
- No new `coverageCore.ts` module (still Phase 169).
- No Essentials/public-facing UI.
- Legend restyle beyond what the new fill requires (a UI-phase concern — roadmap flags `UI hint: yes`).
</domain>

<decisions>
## Implementation Decisions

### Race-Tier Aggregation (ELEC-04)
- **D-01:** A race's tier = the **weakest active candidate** (ALL / min rule). A race is **Tier 3** only if *every* active candidate has names + stances + motivations; **Tier 2** if every active candidate has names + (stance OR motivation); **Tier 1** if it has ≥1 active candidate (names); **Tier 0** if no active candidates. Chosen for anti-inflation consistency with Phase 168's truthfulness fix — the map shows "fully covered" only when no candidate is missing data.
- **D-02:** **Exclude `race_candidates.candidate_status = 'withdrawn'`** from the aggregation and denominator (matches `readrankService.ts`, which already excludes withdrawn). A withdrawn candidate's missing data must not cap the race. Note: this **diverges from Phase 168's `candidate_count`** (raw `COUNT(rc.id)`, no status filter) — the tier metric uses a consistent **active-only** candidate set. Planner should decide whether Tier-1 "has a name" breadth for this phase's panel/fill also moves to active-only for internal consistency (recommended) while leaving `getElectionsCountyScores`/county breadth on the existing raw count.
- **D-03:** Candidates with **`politician_id IS NULL`** (challengers seeded name-only, no linked politician) **count and cap their race at Tier 1** — they genuinely have no stance/motivation data, so the race honestly isn't fully covered. This may make Tier 2/3 hard to reach where name-only challengers exist; that reflects the real state of the data and is the intended (truthful) behavior.

### Map Fill / Headline Metric (ELEC-06)
- **D-04:** The state choropleth fill (and the state's headline number) is a **weighted depth score**: each race contributes its tier as a fraction — **T0 = 0, T1 = ⅓, T2 = ⅔, T3 = 1** — averaged across the state's statewide/legislative races, scaled 0..100. A names-only state reads ~33% (not fully covered, satisfying ELEC-06 / success-criterion 3); a T2-heavy state colors distinctly "more done" than a T1 state. Uses all three tiers in the color. Slots into Phase 168's existing single-hue 0..100 ramp with no legend redesign required.
- **D-05:** **N/A carries forward from Phase 168 D-03** — a state with **zero statewide/legislative races** (denominator 0) still shows "N/A — no statewide/legislative races" via the `unknown`/`scored` vocabulary, never a fake 0% or 100%. The weighted score only applies when ≥1 statewide/legislative race resolves.

### Signal Definitions (ELEC-04) — reuse the completeness map's exact signals
- **D-06:** **`has stances` = ≥1 row in `inform.politician_answers`** for the candidate's `politician_id` — the exact "researched" signal `coverageMapService.statsByJurisdiction` uses. **MUST NOT** use `politicians.last_stances_researched_at` (documented landmine: unstamped for bulk-loaded states like CA/OR, badly under-reports).
- **D-07:** **`has motivations` = ≥1 contribution** joined via `transparent_motivations.politician_sources.essentials_politician_id → transparent_motivations.contributions` — the exact "withDonors" signal from `coverageMapService.ts` (lines ~221–225). Access via `pool.query()` only (the `transparent_motivations` schema is not PostgREST-exposed).
- **D-08:** Both signal thresholds are **≥1** (any stance / any contribution), keeping the tier metric's definition of these signals identical to the 7-axis completeness map — one definition across the admin tool.

### Claude's Discretion (planner / UI-phase)
- Exact panel readout shape: per-race tier badges, per-tier totals ("Tier 3: 2/13 · Tier 2: 4/13 · Tier 1: 13/13"), whether the panel header also shows the weighted score. Success criteria require covered/total by tier + a per-race tier — the specific visual is open.
- Legend styling for the tiered fill (continuous ramp vs tier bands) — leans to a UI phase.
- SQL shape: extend `racesForStateDate`'s query to return per-race active-candidate count + count-with-stances + count-with-motivations (enabling the min/ALL classification), vs a companion query. Keep it within the existing per-state loop + 10-min cache; no new cache keys where avoidable (Phase 168 pattern).
- The precise `StateElection`/`RaceRow` payload extension (tier per race + per-tier tallies + the weighted score field).
- Whether to name the tier classifier as a small pure helper beside `classifyRaces`/`raceCoverage` in `electionsMap.ts` (recommended — pure, unit-testable, reusable by Phases 169/170 later).
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`classifyRaces(races, countyOcdToFips, placeSlugToFips)`** (electionsMap.ts) — already partitions statewide/legislative vs county-pinnable; the tier classifier runs over its `statewide` output.
- **`raceCoverage(races)`** (electionsMap.ts) — the breadth helper being superseded by the tiered metric for the statewide panel/fill; keep it (county side still uses it).
- **`coverageMapService.statsByJurisdiction` SQL** (~lines 197–230) — the authoritative pattern for the two `FILTER (...)` joins: `inform.politician_answers` (stances) and `transparent_motivations.politician_sources → contributions` (motivations). Mirror these joins, but aggregate **per race** (via `race_candidates.race_id`) instead of per jurisdiction.
- **10-min in-process cache** (`cached()` in electionsMapService.ts) — extend the cached payload shape rather than adding cache keys (Phase 168 held to a single `'elections:us'` key).

### Established Patterns
- **`race_candidates.politician_id` is nullable** and carries `candidate_status` (`'active'`/`'withdrawn'`). Tier signals join `race_candidates → politicians (via politician_id) → inform.politician_answers / transparent_motivations`. Null `politician_id` ⇒ no stance/motivation possible (see D-03).
- **The min/ALL rule maps cleanly to SQL per race:** `active = count of non-withdrawn candidates`; `stanced = count of those with ≥1 answer`; `motivated = count of those with ≥1 contribution`. Then T3 iff `active>0 AND stanced=active AND motivated=active`; T2 iff `active>0 AND (stanced=active OR motivated=active)`; T1 iff `active>0`; else T0.
- **Nearest-upcoming-election-date semantics** (`nextElectionDate`) anchor both state and county numbers — keep the tiered statewide number anchored to the same date (denominator consistency, per Phase 168 ELEC-03).
- Elections mode has a single-hue ramp + `StatewideRacesPanel` (no `CoverageTable` in elections mode); the tier readout extends the existing panel.

### Integration Points
- `getElectionsStateScores()` return value flows unmodified through `admin.ts` to `CoverageMap`/`StatewideRacesPanel` — extending `StateElection` is sufficient; no route code change (proven in 168-01).
- The county-pinnable path (`getElectionsCountyScores`, `classifyCounty`) is intentionally left on breadth — do not repoint it (D, scope).
</code_context>

<specifics>
## Specific Ideas

- **Anti-inflation is the north star**, mirroring Phase 168: a race is only as covered as its weakest active candidate, and name-only challengers honestly cap a race at Tier 1. The metric must never make a state look more complete than its actual civic data.
- **Consistency with the completeness map**: "has stances" and "has motivations" use the *identical* data signals the 7-axis map already uses — do not invent a second definition of these signals in the codebase.
- **Tier 0 vs Tier 1 distinction matters**: "race exists, nobody loaded" (T0) is a different admin action than "candidates loaded, no depth yet" (T1) — keep them separate in both the score (0 vs ⅓) and the panel.
</specifics>

## Deferred Ideas

- **Apply tiers to the county drill-down** (`classifyCounty`) — deliberately deferred; Phases 169/170 rework the county/city side, so repointing it now is rework. The tier classifier is built pure/reusable so those phases can adopt it.
- **Fuller stance bar** (require a majority of topics rather than ≥1 answer) — considered and rejected for this phase to stay consistent with the completeness map's ≥1 definition; a later depth-refinement could revisit.
- **Metric-toggle sub-control** to switch the choropleth between breadth and the tiered score — considered, not in scope (adds interaction surface).
- **Tier-band legend restyle** (three discrete swatches instead of a continuous ramp) — a UI-phase (`gsd-ui-phase 168.1`) concern if pursued.
