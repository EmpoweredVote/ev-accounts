<objective>
Fix the Michigan bug at its root: `getElectionsStateScores()` in `backend/src/lib/electionsMapService.ts` (lines 121-140) currently lumps every race at a state's nearest election date — statewide, legislative, county, and place level — into one `raceCoverage()` call, so a state with only statewide/legislative races paints an undifferentiated 100% while every county reads empty. This plan partitions that computation into two separately-computed numbers per state (statewide/legislative vs county/local-pinnable) using the **same** `resolveRaceCountyFips` classifier the county endpoint already uses, and extends the `elections:us` payload to carry both numbers (N/A-safe) plus the statewide race list the panel needs — with no new query, no new cache key, and no schema change.

This is the authoritative payload contract for the phase. Plans 02 (route test) and 03 (frontend) consume the `StateElection` shape defined here.

Implements ELEC-01 (two separate metrics per state — per D-01 the `coverage` field is repointed to the statewide/legislative number that colors the map) and ELEC-03 (consistent denominators — same classifier, same race set, same date anchor as the county endpoint). Reuses `resolveRaceCountyFips` in place per D-04 (no `coverageCore.ts` this phase — that is Phase 169).

Purpose: eliminate the internally-contradictory state-vs-county numbers by defining the geographic-scope buckets exactly once.
Output: extended `electionsMap.ts` (pure partition helper + tests), corrected `getElectionsStateScores`, extended `StateElection` backend type.
</objective>
